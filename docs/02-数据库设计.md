## 1. 存储选型：为什么改为关系型数据库

### 1.1 决策结论

本项目**不使用 JSON 文件作为存储**。业务数据的唯一持久化载体是 HarmonyOS 内置的 `RelationalStore`（SQLite），
应用沙箱 `filesDir` 下不再出现任何承载业务数据的 `.json` 文件。

| 决策项 | 结论 |
| :--- | :--- |
| 存储引擎 | `@kit.ArkData` 的 `relationalStore` |
| 库文件 | `wisdomdaily.db`，单库、多表 |
| 版本管理 | `store.version`（SQLite `user_version`）+ 迁移器列表 |
| 隔离级别 | WAL 日志模式；写操作显式事务；`synchronous = FULL` |
| 安全等级 | `SecurityLevel.S1`（应用私有，随卸载清除） |
| 备份恢复 | `store.backup()` / `store.restore()`，数据库级一致快照 |

### 1.2 历史方案（已废弃）与它的问题

旧版把数据存成**沙箱内的 JSON 文档**，按学期 / 时间模板 / 班级切分文件：

```
<filesDir>/default_setting.json          ← 全局设置（学期列表、当前下标）
<filesDir>/courses/course_<学期名>.json  ← 一个学期的整棵课表对象图
<filesDir>/schedule/schedule_<模板名>.json
<filesDir>/Class/Class_<班级名>.json     ← 班级名单
```

这套方案在"单机 + 小数据量"时能跑，但它把**四个致命问题**留在了应用层：

| # | 问题 | 具体后果 |
| :--- | :--- | :--- |
| 1 | **非原子写入** | `openSync(TRUNC)` 先清空再写。清空后、写完前进程被杀 ⇒ 一整个学期课表归零 |
| 2 | **无引用完整性** | 删除课程不会清理班级名单，班级改名会让名单变成孤儿文件（数据"消失"） |
| 3 | **无索引、全量重写** | 改一个教室备注也要重写整个学期 JSON；所有查询都是内存线性遍历 |
| 4 | **关联靠文件名** | 学期名被直接拼进文件名，改名 = 数据搬家，极易漏改导致"打开是空的" |

### 1.3 改造后的对照

| 维度 | 旧：JSON 文档 | 新：RelationalStore |
| :--- | :--- | :--- |
| 原子性 | ❌ TRUNC 直接覆盖 | ✅ 事务提交 / 回滚 |
| 引用完整性 | ❌ 应用层弱关联 | ✅ 外键 + 应用层显式级联（双保险） |
| 写入成本 | ❌ 整学期重写 | ✅ 行级 UPDATE（改一个教室 = 一条语句） |
| 查询能力 | ❌ 全量加载 + 线性遍历 | ✅ 索引 + JOIN + 视图 |
| 关联键 | ❌ 名称（会被改名破坏） | ✅ 不可变 UUID / 主键 |
| 计数一致性 | ❌ 冗余计数列会漂移 | ✅ 由 `COUNT` 实时算出 |
| 备份 | ⚠️ 多文件，可能半套成功 | ✅ 数据库级一致快照 |
| 可人工编辑 | ✅ 文本编辑器直接改 | ⚠️ 需 SQLite 工具（用导出功能替代） |

> **取舍说明**：关系库牺牲了"用户拿文本编辑器就能改数据"这一点。补偿手段是导出功能
> （`RelationalStore` 原生备份 + 业务层 CSV 导出），并且换来的是"进程随时被杀也不丢数据"。

### 1.4 旧数据如何过来

不是并行维护两套存储，而是**一次性单向搬迁**：见 §9。

## 2. 数据库物理设计

### 2.1 库文件与运行期参数

```
<filesDir>/databases/wisdomdaily.db        主库文件
<filesDir>/databases/wisdomdaily.db-wal    WAL 预写日志
<filesDir>/databases/wisdomdaily.db-shm    共享内存索引
<filesDir>/wisdomdaily_backup.db           用户备份产物（store.backup 的输出）
<filesDir>/legacy_json_backup/             旧 JSON 数据归档（迁移后保留一个版本周期）
```

连接建立后依次执行（`db/TableSchema.ets` 的 `PRAGMA_SETUP`）：

```sql
PRAGMA foreign_keys = ON;   -- 打开外键约束
PRAGMA journal_mode = WAL;  -- 读写并发，崩溃不损坏主库
PRAGMA synchronous = FULL;  -- 提交即落盘，优先数据安全（本应用写入频率低）
```

> **关于外键的一处工程事实**：SQLite 的外键开关是"每连接"生效的，而 `RelationalStore`
> 内部维护连接池，不保证每条连接都吃到这个 PRAGMA。因此本项目同时实现了
> **应用层显式级联删除**（`SemesterDao.deleteCascade` / `CourseDao.deleteCascade` /
> `TeacherDao.deleteCascade` / `CourseDao.deleteGroup`），两条路径互为兜底，
> 任何情况下都不会留下孤儿行。详见 §8。

### 2.2 容量估算

| 表 | 单学期估算行数 | 单行字节 | 小计 |
| :--- | ---: | ---: | ---: |
| `semester` | 1 ~ 6 | ~80 | < 1 KB |
| `schedule_template` | 1 ~ 6 | ~70 | < 1 KB |
| `schedule_slot` | 12 ~ 24 / 模板 | ~30 | 数 KB |
| `teacher` | 30 | ~90 | ~3 KB |
| `course` | 40 / 教师 ⇒ 400 ~ 1200 | ~110 | ~130 KB |
| `class_info` | 100 ~ 300 | ~50 | ~15 KB |
| `class_group` | 每课程 1 ~ 5 ⇒ 1000 ~ 3000 | ~70 | ~200 KB |
| `time_period` | 每分组 1 ~ 3 ⇒ 2000 ~ 6000 | ~60 | ~350 KB |
| `period_week` | 每时间段 2 ~ 20 ⇒ 20 000 ~ 60 000 | ~20 | ~1.2 MB |
| `student` | 每班 40 ⇒ 4000 ~ 12000 | ~80 | ~1 MB |
| `attendance` | 每次点名 × 该班人数 ⇒ 500 ~ 3000 | ~70 | ~200 KB |
| **合计** | | | **约 3 MB / 学期上限** |

按"每学期一个 `semester` 行、数据不跨学期共享"的模型，5 个学期约 15 MB，
仍在移动端可接受范围（旧 JSON 方案同规模下是 5 × 300 KB 文本 + 解析开销，
行数一多就靠内存硬扛）。若未来学期数继续增长，`period_week` 是第一优化目标——
可改为位图（`INTEGER` 存 64 位周次掩码）把该表体积压缩 90%。

### 3.2 与旧结构的三处结构性改进

这三处不是"换个存法"，而是修掉了旧设计里无法在应用层彻底解决的问题：

**改进一：新增 `class_info`，班级拥有不可变身份**

旧结构里 `CourseInformation.class_name` 既是显示名、又是与名单文件的关联键。
班级一改名，`Class/Class_<旧名>.json` 就成了孤儿。

```
旧： CourseInformation.class_name ──(按名字拼文件名)──▶ Class/Class_<班名>.json
新： class_group.class_id ─(外键)─▶ class_info.class_id ─(外键)─▶ student.class_id
     class_info.class_name 只用于显示，随便改；关联走 class_id
```

**改进二：`week_nums` 拆成 `period_week` 子表**

`[1,3,5,7]` 这种数组塞在 JSON 里，SQL 完全用不上。拆表之后：

- "第 8 周有哪些课" 变成一次索引查询，而不是全量遍历；
- 周次交集可以下推到 SQL 做冲突检测（`pw.week_no IN (?,?,…)`）；
- 周次越界由 `CHECK (week_no BETWEEN 1 AND 60)` 兜住，物理上不可能出现"第 0 周"。

**改进三：消灭会漂移的冗余数据**

| 旧字段 | 问题 | 新做法 |
| :--- | :--- | :--- |
| `citation_count` | 计数列，与真实引用会不同步，不同步就会"删掉被引用的模板" | 由 `v_template_stat` 视图实时 `COUNT` |
| `class_time[][]` | 二维数组长度与 `class_sessions` 可能不一致 | `schedule_slot` 子表，行数就是节数 |
| `Student.class_name` | 冗余班名，两处不一致就无法判定 | 只存 `class_id`，需要时 JOIN |
| `Student.telephone: number` | 丢前导 0 | `TEXT` |
| `Student.remake` | 拼写错误 | 修正为 `remark`（导入时自动映射） |
| 空学分默认补 2 | 与"可不填"语义冲突 | `REAL NULL`，真的空 |

### 3.3 关系与完整性约束矩阵

| 父 → 子 | 基数 | 外键 | 删除策略 | 说明 |
| :--- | :--- | :--- | :--- | :--- |
| `schedule_template` → `schedule_slot` | 1:N | `schedule_id` | CASCADE | 模板删除，节次表一起走 |
| `schedule_template` → `semester` | 1:N | `semester.schedule_id` | SET NULL | 模板被删，学期变"未绑定"而不是被删 |
| `semester` → `teacher` | 1:N | `semester_id` | CASCADE | 删学期，教师一起走 |
| `semester` → `course` | 1:N | `semester_id` | CASCADE | 同上 |
| `semester` → `app_setting` | 1:0..1 | `app_setting.semester_id` | SET NULL | 当前学期被删，指向清空后自动修复 |
| `teacher` → `course` | 1:N | `teacher_id` | CASCADE | 删教师，其课程一起走 |
| `teacher` → `app_setting` | 1:0..1 | `app_setting.teacher_id` | SET NULL | 同上 |
| `course` → `class_group` | 1:N | `course_id` | CASCADE | 删课程，班级分组一起走 |
| `class_info` → `class_group` | 1:N | `class_id` | RESTRICT | 仍被课程引用时不允许删班级档案 |
| `class_group` → `time_period` | 1:N | `class_group_id` | CASCADE | |
| `time_period` → `period_week` | 1:N | `time_period_id` | CASCADE | |
| `class_info` → `student` | 1:N | `class_id` | CASCADE | 删班级档案，名单一起走 |

## 4. 表结构详细定义

### 4.1 `schedule_template` — 课表时间模板（作息表）

```sql
CREATE TABLE IF NOT EXISTS schedule_template (
  id             INTEGER PRIMARY KEY AUTOINCREMENT,
  name           TEXT    NOT NULL UNIQUE,
  class_sessions INTEGER NOT NULL DEFAULT 12 CHECK (class_sessions BETWEEN 1 AND 24),
  duration_time  INTEGER NOT NULL DEFAULT 45 CHECK (duration_time BETWEEN 1 AND 300),
  is_builtin     INTEGER NOT NULL DEFAULT 0  CHECK (is_builtin IN (0, 1)),
  created_at     INTEGER NOT NULL DEFAULT 0,
  updated_at     INTEGER NOT NULL DEFAULT 0
);
```

| 字段 | 类型 | 必填 | 默认 | 约束 / 说明 |
| :--- | :--- | :--- | :--- | :--- |
| `id` | INTEGER | 是 | 自增 | 主键 |
| `name` | TEXT | 是 | — | **UNIQUE**。旧版是"模板名 = 文件名"，现在名字与存储彻底解耦 |
| `class_sessions` | INTEGER | 是 | 12 | 每天总节数，决定课表网格行数；1 ~ 24 |
| `duration_time` | INTEGER | 是 | 45 | 每节时长（分钟），仅展示 |
| `is_builtin` | INTEGER | 是 | 0 | 1 = 内置"默认"模板，受保护不可删 |
| `citation_count` | — | — | — | **不是列**：由 `v_template_stat` 视图实时算出 |

**为什么不落 `citation_count`**：旧版把它当作持久化字段，一旦与真实引用不同步，
就会允许删除仍被学期引用的模板。改成视图实时 `COUNT` 之后，这类脏状态在物理上不存在。

### 4.2 `schedule_slot` — 节次时间明细

```sql
CREATE TABLE IF NOT EXISTS schedule_slot (
  schedule_id INTEGER NOT NULL,
  session_no  INTEGER NOT NULL CHECK (session_no BETWEEN 1 AND 24),
  start_time  TEXT    NOT NULL,     -- 'HH:mm'
  end_time    TEXT    NOT NULL,
  PRIMARY KEY (schedule_id, session_no),
  FOREIGN KEY (schedule_id) REFERENCES schedule_template(id) ON DELETE CASCADE
);
```

| 字段 | 类型 | 说明 |
| :--- | :--- | :--- |
| `schedule_id` | INTEGER | 联合主键，所属模板 |
| `session_no` | INTEGER | 联合主键，第 N 节（1-based） |
| `start_time` / `end_time` | TEXT | `HH:mm`；第 1~4 节上午、5~8 节下午、9~12 节晚上由数据决定，不写死在代码里 |

**替换关系**：旧 `class_time: string[][]` → 本表。行数天然等于 `class_sessions`，
不会再出现"节数说 12、时间表只有 10 行"的错位。

### 4.3 `semester` — 学期

```sql
CREATE TABLE IF NOT EXISTS semester (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  name        TEXT    NOT NULL UNIQUE,
  total_weeks INTEGER NOT NULL DEFAULT 20 CHECK (total_weeks BETWEEN 1 AND 60),
  start_date  TEXT    NOT NULL DEFAULT '',   -- 第 1 周周一，'YYYY-MM-DD'
  schedule_id INTEGER,
  sort_order  INTEGER NOT NULL DEFAULT 0,
  created_at  INTEGER NOT NULL DEFAULT 0,
  updated_at  INTEGER NOT NULL DEFAULT 0,
  FOREIGN KEY (schedule_id) REFERENCES schedule_template(id) ON DELETE SET NULL
);
```

| 字段 | 类型 | 必填 | 说明 |
| :--- | :--- | :--- | :--- |
| `name` | TEXT | 是 | **UNIQUE**。旧版靠"重名自动加 (1) 后缀 + 改文件名"实现，现在由 UNIQUE 约束直接拒绝并给出友好提示 |
| `total_weeks` | INTEGER | 是 | 1 ~ 60 |
| `start_date` | TEXT | 是 | `YYYY-MM-DD`。**旧数据 `2025/9/1` 在导入时归一化**，并修掉"起始日非周一时算出第 0 周" |
| `schedule_id` | INTEGER | 否 | 引用作息模板；NULL = 未绑定（模板被删时自动置 NULL，而不是把学期一起删掉） |
| `sort_order` | INTEGER | 是 | 用户看到的学期顺序 |

**为什么不再用"数组下标"表示当前学期**：`semesters[] + semester_index` 的模型在删除 /
重排学期后会静默指向另一个学期——这就是"切学期后显示别人的课表"的根因。
现在 `app_setting.semester_id` 存真实主键，删学期时外键 SET NULL + `repairPointers()`
自动落到第一个学期，指向永远明确。

### 4.4 `teacher` — 教师

```sql
CREATE TABLE IF NOT EXISTS teacher (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  semester_id INTEGER NOT NULL,
  staff_no    INTEGER NOT NULL,
  name        TEXT    NOT NULL,
  department  TEXT,
  age         INTEGER,
  sex         TEXT,
  telephone   TEXT,
  sort_order  INTEGER NOT NULL DEFAULT 0,
  created_at  INTEGER NOT NULL DEFAULT 0,
  updated_at  INTEGER NOT NULL DEFAULT 0,
  UNIQUE (semester_id, staff_no, name),
  FOREIGN KEY (semester_id) REFERENCES semester(id) ON DELETE CASCADE
);
```

| 字段 | 类型 | 说明 |
| :--- | :--- | :--- |
| `staff_no` | INTEGER | 工号（原 `Teacher.id`），如 `2024***25` |
| `name` | TEXT | 姓名 |
| `department` / `age` / `sex` / `telephone` | TEXT/INTEGER/TEXT/TEXT | 全部可空（NULL = 未填） |
| — | — | **UNIQUE (semester_id, staff_no, name)**：同一教师重复导入只做字段合并（`COALESCE` 更新），不追加重复行 |

### 4.5 `course` — 课程

```sql
CREATE TABLE IF NOT EXISTS course (
  id            INTEGER PRIMARY KEY AUTOINCREMENT,
  course_id     TEXT    NOT NULL UNIQUE,     -- 不可变业务主键（UUID）
  semester_id   INTEGER NOT NULL,
  teacher_id    INTEGER NOT NULL,
  course_name   TEXT    NOT NULL,
  course_type   TEXT    NOT NULL DEFAULT '理论' CHECK (course_type IN ('理论', '实验', '实践')),
  course_score  REAL    CHECK (course_score IS NULL OR (course_score > 0 AND course_score <= 30)),
  course_remark TEXT    NOT NULL DEFAULT '',
  sort_order    INTEGER NOT NULL DEFAULT 0,
  created_at    INTEGER NOT NULL DEFAULT 0,
  updated_at    INTEGER NOT NULL DEFAULT 0,
  UNIQUE (teacher_id, semester_id, course_name, course_type),
  FOREIGN KEY (semester_id) REFERENCES semester(id) ON DELETE CASCADE,
  FOREIGN KEY (teacher_id)  REFERENCES teacher(id)  ON DELETE CASCADE
);
```

| 字段 | 类型 | 说明 |
| :--- | :--- | :--- |
| `course_id` | TEXT | UUID，**导入旧数据时若缺失则补生成**，从此课程有稳定身份 |
| `course_score` | REAL | **可为 NULL**，真正的"未填"。旧的 `?? 2` 默认值已被移除 |
| `course_type` | TEXT | CHECK 限制为 理论 / 实验 / 实践 三选一 |
| — | — | **UNIQUE (teacher_id, semester_id, course_name, course_type)**：旧版靠 `find()` 在内存里守这个唯一性，现在由数据库守，并发/重复导入都不会产生重复课程 |

### 4.6 `class_info` — 班级档案（新增表）

```sql
CREATE TABLE IF NOT EXISTS class_info (
  class_id   TEXT    PRIMARY KEY,          -- 不可变 UUID
  class_name TEXT    NOT NULL UNIQUE,
  created_at INTEGER NOT NULL DEFAULT 0,
  updated_at INTEGER NOT NULL DEFAULT 0
);
```

| 字段 | 类型 | 说明 |
| :--- | :--- | :--- |
| `class_id` | TEXT | 主键，UUID。所有关联（`class_group`、`student`）都用它 |
| `class_name` | TEXT | **UNIQUE**，纯显示名。改名 = 一条 `UPDATE`，所有引用自动跟随 |

### 4.7 `class_group` — 课程 × 班级（原 `CourseInformation`）

```sql
CREATE TABLE IF NOT EXISTS class_group (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  course_id  INTEGER NOT NULL,
  class_id   TEXT    NOT NULL,
  population INTEGER NOT NULL DEFAULT 0 CHECK (population >= 0),
  color      TEXT    NOT NULL DEFAULT '#F0F0F0'
             CHECK (color GLOB '#[0-9A-Fa-f][0-9A-Fa-f][0-9A-Fa-f][0-9A-Fa-f][0-9A-Fa-f][0-9A-Fa-f]'
                 OR color GLOB '#[0-9A-Fa-f][0-9A-Fa-f][0-9A-Fa-f][0-9A-Fa-f][0-9A-Fa-f][0-9A-Fa-f][0-9A-Fa-f][0-9A-Fa-f]'),
  sort_order INTEGER NOT NULL DEFAULT 0,
  UNIQUE (course_id, class_id),
  FOREIGN KEY (course_id) REFERENCES course(id)         ON DELETE CASCADE,
  FOREIGN KEY (class_id)  REFERENCES class_info(class_id) ON DELETE RESTRICT
);
```

**`color` 的 CHECK 约束值得单独说明**（v3 起更新）：颜色格式为 8 位 ARGB `#AARRGGBB`
（带真实透明度，ArkUI `backgroundColor` 原生支持），6 位 `#RRGGBB` 也仍合法（视为不透明，
兼容历史数据）。字色反色的老问题由"合成后判亮度"解决，而非丢弃 Alpha：

1. 写入前由 `normalizeColor()` 归一化（`#RGB` / `#RRGGBB` / `#AARRGGBB` → `#AARRGGBB`，
   6 位自动补 `FF`）；
2. 数据库 CHECK 约束（6 位或 8 位十六进制）做最后一道拦截；
3. 自动字色 `textColorOf()` 先把 Alpha 合成到白底（课程卡片渲染在白色页面上），再按
   **WCAG 相对亮度**（sRGB 线性化 + 0.2126/0.7152/0.0722）判黑/白，取对比度更高的一侧
   （阈值 `L > 0.1791` 用黑字）；半透明深色不再误判，也修正了旧 BT.601 方案在
   `#1890FF` 这类中亮蓝上误配白字（3.24:1 → 6.47:1）的问题；
4. v3 迁移（`rebuildClassGroupForArgb`）重建本表放宽 CHECK，并把存量 6 位色补 `FF` 前缀。

| 字段 | 类型 | 说明 |
| :--- | :--- | :--- |
| `id` | INTEGER | `CHECK (id = 1)` ⇒ 表里最多一行 |

| `teacher_id` | INTEGER | 当前教师主键 |
| `theme_mode` | INTEGER | 0 跟随系统 / 1 浅色 / 2 深色 |
| `theme_color` | TEXT | 界面主题色（图标与强调色；ARGB 8 位），落库前经 `normalizeColor()`；非法值读取时用 `colorOr()` 回退默认蓝 |
| `today_color` | TEXT | 高亮色（ARGB 8 位），用于首页周次栏的月份数字与"今天"日期徽标（读同一列，语义随 UI 一处收口，不再新增列） |
| `owner_name` | TEXT | 机主姓名（首启录入）；NULL = 尚未配置 |
| `owner_staff_no` | INTEGER | 机主教师工号；NULL = 尚未配置 |
| `notify_next_day` | INTEGER | 0/1，提醒第二天的课（次日有课时，当天 22:00 提醒） |
| `notify_ahead` | INTEGER | 0/1，当天有课时提前提醒 |
| `notify_ahead_minutes` | INTEGER | 提前量（分钟），默认 20；写入前经 `clampNotifyMinutes()` 收进 [1, 120] |

> **上课提醒三列为什么与界面颜色放在同一张表**：同样是"全局唯一一份、与学期/教师无关"的配置，
> 另建表只会多一次查询与一处事务边界；三列都是 v5 用 `ALTER TABLE ADD COLUMN` 补上的，
> 同样**刻意不加 CHECK**（"新装 = 升级"的结构必须完全一致），取值范围由写入路径兜底。
> 提醒条目本身**不入库** —— 它是"按课表算出来的快照"，每次重建时全清重发（见 `docs/06` §2.8.4）。

> **`theme_color` / `today_color` 为什么不做 CHECK 约束**：这两列是 v4 用
> `ALTER TABLE ADD COLUMN` 补上的，为了让"新装"与"升级"最终结构完全一致，
> 建表语句里也不加 CHECK；格式由写入路径（`normalizeColor()`）和读取路径
> （`colorOr()` 带回退值）双重兜底，界面不会因为一个脏色值而失效。

> **机主（默认教师）语义**：`owner_*` 是跨学期的"我是谁"，teacher 表的行是"某学期里的教师"。
> 首启录入时 `saveOwnerProfile()` 在一个事务里：写 owner 两列 → 在当前学期登记该教师
> （同工号认领；若学期只有未挂课的种子教师则直接改成机主）→ 把 `teacher_id` 指向他。
> 之后 `createSemester()` 会自动在新学期带出这位默认教师。

**旧 `default_setting.json` → 本表的映射**：

| 旧字段 | 新位置 | 说明 |
| :--- | :--- | :--- |
| `semesters: string[]` | `semester` 表多行 | 一份列表变成多行，各自带 `sort_order` |
| `semester_index: number` | `app_setting.semester_id` | 下标 → 主键 |
| `schedules: string[]` | `schedule_template` 表多行 | 同上 |
| `teacher_index: number` | `app_setting.teacher_id` | 下标 → 主键 |

### 4.12 `attendance` — 签到（点名）记录（新增表 · schema v6）

```sql
CREATE TABLE IF NOT EXISTS attendance (
  id             INTEGER PRIMARY KEY AUTOINCREMENT,
  time_period_id INTEGER NOT NULL,
  week_no        INTEGER NOT NULL CHECK (week_no BETWEEN 1 AND 60),
  student_id     INTEGER NOT NULL,
  status         TEXT    NOT NULL DEFAULT 'present'
                 CHECK (status IN ('present', 'absent', 'leave')),
  grade          INTEGER CHECK (grade IS NULL OR (grade >= 1 AND grade <= 5)),
  score          INTEGER CHECK (score IS NULL OR (score >= 0 AND score <= 100)),
  created_at     INTEGER NOT NULL DEFAULT 0,
  updated_at     INTEGER NOT NULL DEFAULT 0,
  UNIQUE (time_period_id, week_no, student_id),
  FOREIGN KEY (time_period_id) REFERENCES time_period(id) ON DELETE CASCADE,
  FOREIGN KEY (student_id)     REFERENCES student(id)     ON DELETE CASCADE
);
```

| 字段 | 类型 | 说明 |
| :--- | :--- | :--- |
| `time_period_id` + `week_no` | INTEGER | 定位"哪一次课"。`time_period` 是**每周复用**的（第 1 周周一第 1 节与第 2 周周一第 1 节是同一条记录），只用 `time_period_id` 会把两周混成一次 |
| `student_id` | INTEGER | 谁。与上两列组成唯一键 ⇒ 一个学生一次课最多一条 |
| `status` | TEXT | `present` 出勤 / `absent` 旷课（导出 `×`）/ `leave` 请假（导出 `⊕`）—— 与建表语句的 CHECK 一一对应 |
| `grade` | INTEGER | 长按下滑选的等级 1~5；`NULL` = 未评（旷课与请假也写 NULL，**不写 0**） |
| `score` | INTEGER | 等级换算出的分数，**选等级那一刻当场算好落库**；旷课/请假为 NULL |

> **为什么分数要落库而不是导出时现算**：同一份点名记录导两次分数不一样，老师没法拿它对账，学生来问也说不清。等级与分数在 `SignInMark.markGrade()` 里一起写入，导出只做"取值"。

> **"没点过名"在库里不占行**：老师点完一轮就是一份完整快照，点「完成」时 `replaceSession` 先清本次课、再整批写（单事务、天然幂等）。因此"这次课只写了三个人"这种中间态不会存在，也没有`status = 'none'`这种取值。

> **两个父表 ⇒ 级联要显式清**：`attendance` 同时挂在 `time_period` 与 `student` 上，而本工程的级联删除是显式写在各 DAO 里的（`PRAGMA foreign_keys` 在连接池下不保证生效）。与其在"删课程 / 删班级 / 删时段 / 删周次 / 删教师 / 删学期 / 删学生"七个入口各写一条形态不同的 DELETE，不如收口成一条与来源无关的幂等语句 `AttendanceDao.pruneOrphans`（见 §8）。

## 5. 视图设计

### 5.1 `v_lesson` — 扁平化的"一次上课"

```sql
CREATE VIEW IF NOT EXISTS v_lesson AS
SELECT c.id AS course_row_id, c.course_id, c.course_name, c.course_type,
       c.course_score, c.course_remark, c.semester_id, c.teacher_id,
       t.staff_no, t.name AS teacher_name,
       cg.id AS class_group_id, cg.class_id, ci.class_name, cg.population, cg.color,
       tp.id AS time_period_id, tp.weekday, tp.start_time, tp.end_time, tp.class_room, tp.remark,
       pw.week_no
  FROM course c
  JOIN teacher     t  ON t.id = c.teacher_id
  JOIN class_group cg ON cg.course_id = c.id
  JOIN class_info  ci ON ci.class_id = cg.class_id
  JOIN time_period tp ON tp.class_group_id = cg.id
  JOIN period_week pw ON pw.time_period_id = tp.id;
```

六表 JOIN 拍平成一行一次上课，于是课表要的各种视角都变成一条 SQL：

| 视角 | 查询（`dao/LessonDao.ets`） |
| :--- | :--- |
| 某教师第 N 周的课（**课表主视图数据源**） | `WHERE semester_id=? AND teacher_id=? AND week_no=?` |
| 某班第 N 周的课（可能跨教师） | `WHERE semester_id=? AND class_id=? AND week_no=?` |
| 某周全校所有课（周课时统计） | `WHERE semester_id=? AND week_no=?` |
| 某周用到的教室（排课复盘） | `SELECT DISTINCT class_room …` |

> **用途边界（重要）**：视图会按周次展开行数（一条 20 周的时间段 → 20 行）。
> 所以它**只用于按周取数**。冷启动组装整学期对象图走的是各表直查 + 内存拼装
> （见 §6.3），学期规模下能膨胀到几万行，用视图会得不偿失。

### 6.2 关键查询

**Q1 — 课表主视图（某教师第 8 周、周三）**

```sql
SELECT course_name, class_name, color, class_room, start_time, end_time
  FROM v_lesson
```

**Q2 — 班级维度冲突检测（周次交集 + 节次重叠 + 周次下推）**

```sql
SELECT DISTINCT tp.id, tp.start_time, tp.end_time, tp.class_room, c.course_name, ci.class_name
  FROM time_period tp
  JOIN class_group  cg ON cg.id = tp.class_group_id
  JOIN course        c ON c.id  = cg.course_id
  JOIN class_info   ci ON ci.class_id = cg.class_id
  JOIN period_week  pw ON pw.time_period_id = tp.id
 WHERE c.semester_id = ?
   AND tp.weekday    = ?              -- 星期相同
   AND tp.start_time <= ?             -- 节次区间相交（闭区间）
   AND tp.end_time   >= ?
   AND tp.id <> ?                     -- 编辑自己时排除自己
   AND cg.class_id IN (?, ?, …)       -- 本次提交涉及的班级
   AND pw.week_no  IN (?, ?, …);      -- 本次提交涉及的周次 ← 周次交集交给索引
```

```sql
  FROM class_group cg
  JOIN course     c  ON c.id = cg.course_id
  JOIN class_info ci ON ci.class_id = cg.class_id
```

### 6.3 冷启动读路径（组装整学期对象图）

刻意**不用** `v_lesson`：视图按周展开会让 3000 个时间段变成 6 万行。
实际做法是 6 条直查 + 内存拼装（`ScheduleRepository.loadSemesterCourses`）：

| # | 查询 | 返回 |
| :--- | :--- | :--- |
| 1 | `semester` 按 id（联 `schedule_template` 取名） | 1 行 |
| 2 | `teacher` 按 `semester_id` | N 教师 |
| 3 | `course` 按 `semester_id` | M 课程 |
| 4 | `class_group` JOIN `class_info` 按 `semester_id` | K 分组 |
| 5 | `time_period` JOIN `class_group`+`course` 按 `semester_id` | T 时间段 |
| 6 | `period_week` JOIN 同样链，`week_no <= total_weeks` | W 周次行 |

然后在内存里按 `class_group_id → course_id → teacher_id` 逐层归组（每层一个 `Map`），
得到 `SemesterCourses` 对象图。**6 次查询与学期大小无关**，不存在 N+1。

## 7. 事务边界

**事务是本次改造的核心收益**。所有会跨多表的写操作都包在 `createTransaction()` 里，
失败整体回滚；不存在"改了一半"的中间状态。

| 用例 | 涉及表 | 事务边界 | 失败后果 |
| :--- | :--- | :--- | :--- |
| 首启初始化 / 种子数据 | 6 张 | `doInit` 内一个事务 | 库保持空，下次启动重试 |
| 旧 JSON 一次性导入 | 9 张 | 整个导入一个事务 | 旧文件不搬家，可重试 |
| 新增 / 修改时间段（含周次） | `time_period` + `period_week` | 一个事务 | 不会出现"时间段在、周次没了" |
| 保存课程 + 班级分组 | `course` + `class_group` + `class_info` | 一个事务 | 不会出现"课程在、班级没了" |
| 删除课程 | 4 张（含周次） | 一个事务 | 不会留下孤儿时间段 |
| 删除学期 | 6 张 + 修复 `app_setting` | 一个事务 | 不会出现半个学期残留 |
| 删除教师 | 5 张 + 修复 `app_setting` | 一个事务 | 同上 |
| 整班名单替换 | `student` | 一个事务 | 不会出现"清空了但没写进去" |
| **一次课的点名结果整批替换** | `attendance`（先删本次课 → 再 batchInsert） | 一个事务 | 不会出现"清空了但没点进去"；老师点完一轮就是一整份快照，重复点「完成」不产生重影行 |
| 切换当前学期 / 教师 | `app_setting` | 一个事务 | — |
| 模板节次表更新 | `schedule_template` + `schedule_slot` | 一个事务 | 节数不会与行数错位 |

> 单条 `executeSql` 在 `RelationalStore` 里本身就是自动提交的原子操作。
> 只有"多表/多行必须同生共死"的场景才开显式事务——这也是为什么轻量编辑
> （改一个教室、改一个周次）走单语句，不额外开事务。

## 8. 级联删除：数据库约束 + 应用层显式级联

```
删除一门课程
  ├─ 数据库路径（PRAGMA foreign_keys = ON 生效时）
  │    course ─CASCADE→ class_group ─CASCADE→ time_period ─CASCADE→ period_week
  └─ 应用层路径（CourseDao.deleteCascade，永远执行）
       DELETE period_week WHERE time_period_id IN (…该课程的…)
       DELETE time_period WHERE class_group_id  IN (…该课程的…)
       DELETE class_group  WHERE course_id = ?
       DELETE course       WHERE id = ?
```

两条路径**顺序相同、语义相同**（先子后父），重复执行是幂等的。
之所以两条都留：`PRAGMA foreign_keys` 是每连接生效的开关，而 `RelationalStore`
的连接池不保证每条连接都吃到它。宁可多跑 4 条删除语句，也不接受孤儿数据。

删除的完整链路（自底向上，不可颠倒）：

```
period_week  →  time_period  →  class_group  →  course  →  teacher  →  semester
```

**`class_info` 与 `student` 不参与级联删除**：一个班级档案可能被多个学期的课程引用，
所以 `ClassInfoDao.deleteIfUnused()` 先查引用数，> 0 直接拒绝删除并返回 `false`。

**`attendance` 有两个父表，收口成一条幂等清理语句**：签到行既属于"某一次课"（`time_period`）
又属于"某个学生"（`student`），任何一条删除路径都可能让它变成孤儿。与其在七个删除入口各写一条
形态不同的 DELETE，不如统一调用 `AttendanceDao.pruneOrphans(exec)`：

```sql
DELETE FROM attendance
 WHERE time_period_id NOT IN (SELECT id FROM time_period)
    OR student_id     NOT IN (SELECT id FROM student);
```

**少七处特判，就少七次"新加一条删除路径忘了级联"的机会。**（"删掉某一次课"不属于孤儿清理 —— 时段还在、只是那一周没了，走 `deleteBySession` 精确删。）

## 9. 版本迁移机制

### 9.1 版本号

库版本用 `RelationalStore` 的 `store.version`（即 SQLite `user_version`）管理，
当前 `DB_VERSION = 6`（`db/TableSchema.ets`）。

```
首次安装   : store.version == 0  → 执行 DDL_TABLES / VIEWS / INDEXES（一个事务）→ version = 6
老版本升级 : 0 < store.version < DB_VERSION → 依次执行 MIGRATIONS 中未执行项 → version = DB_VERSION
版本一致   : 校验核心表是否存在（版本号正常但表被清理的情况）→ 缺失则重建
```

### 9.2 迁移规范（`db/DbMigrations.ets`）

当前已发布的迁移：

| targetVersion | 内容 |
| :--- | :--- |
| 2 | `app_setting` 增加 `owner_name TEXT` / `owner_staff_no INTEGER`（首启机主录入）。`PRAGMA table_info` 探测列存在才 ALTER，幂等 |
| 3 | `class_group.color` 升级为 8 位 ARGB `#AARRGGBB`：CHECK 无法 ALTER → 整表重建（建新表 → 拷数据 → 换名），存量 6 位色补 `FF` 前缀。**重建期间必须 `PRAGMA foreign_keys = OFF`**——本表被 `time_period` 以 `ON DELETE CASCADE` 引用，外键开着 DROP 会级联清空全部时间段；另含"中断在 DROP/RENAME 之间则直接补换名"的幂等恢复分支 |
| 4 | `app_setting` 增加界面颜色 `theme_color` / `today_color TEXT NOT NULL DEFAULT '#FF1890FF'`（主题色与今日高亮色）。同样 `PRAGMA table_info` 探测 + `ALTER TABLE ADD COLUMN`，幂等 |
| 5 | `app_setting` 增加上课提醒 `notify_next_day` / `notify_ahead INTEGER NOT NULL DEFAULT 0` 与 `notify_ahead_minutes INTEGER NOT NULL DEFAULT 20`。三列都带 `NOT NULL DEFAULT`，**存量行升级后自动拿到"关闭 + 20 分钟"，不需要补 UPDATE**，也就不会出现半升级的中间态 |
| 6 | **新增 `attendance` 表**（签到记录）。建表语句与 `TableSchema.DDL_ATTENDANCE` **共用同一份常量**（抄两份迟早漂移成两种结构）；`IF NOT EXISTS` ⇒ 幂等，索引由 `migrate()` 末尾重跑 `DDL_INDEXES` 补齐。纯新增表，不动任何既有列，升级不涉及数据搬迁 |

下一段迁移的模板（照抄 v5 / v6 的写法；注意 ArkTS 严格模式禁止"接口 + 对象字面量内联函数"，
迁移项一律 `new Migration(...)`）：

```ts
new Migration(7,
  'semester 表增加某开关',
  async (store: relationalStore.RdbStore): Promise<void> => {
    const has: boolean = await hasColumn(store, Tables.SEMESTER, 'some_flag');
    if (!has) {
      await store.execute(`ALTER TABLE semester ADD COLUMN some_flag INTEGER NOT NULL DEFAULT 1`);
    }
  })
```

**硬性规范**：

1. 迁移只能向前，不允许回头改已发布的迁移项；
2. 每项必须**幂等**——中途崩溃会重跑；
3. 移动端优先用 `ALTER TABLE … ADD COLUMN + 默认值`；仅当必须修改 CHECK / 列类型等
   无法 ALTER 的约束时才允许整表重建（参照 v3：关外键防级联误删 + 中断恢复分支）；
4. 新增列之后，`TableSchema` 的建表语句必须同步更新，保证"新装"与"升级"最终结构完全一致
   （迁移流程末尾会把 `DDL_TABLES / VIEWS / INDEXES` 再补执行一遍，全部 `IF NOT EXISTS`，幂等）。

| 场景 | 机制 | 一致性 |

## 13. 遗留风险与后续优化

| # | 项 | 现状 | 建议 |
| :--- | :--- | :--- | :--- |
| D-1 | `period_week` 行数最多 | 每时间段每生效周一行 | 数据量再上一个量级时改为 64 位周次掩码存单行，可压缩 90% |
| D-2 | `PRAGMA foreign_keys` 连接池不确定 | 已有应用层显式级联兜底 | 若后续发现某机型上 `PRAGMA` 未生效，不影响正确性，仅多打日志 |
| D-3 | 冲突检测串行两次查询 | 教师维度 + 班级维度各一次 SQL | 可合并为一次 `UNION ALL`；当前开销在索引下可忽略 |
| D-4 | `class_info` 无引用计数缓存 | 每次删班级都查一次 `COUNT` | 班级档案量级很小，暂不引入缓存 |
| D-5 | 无全文检索 | 课程名精确匹配 | 量大时引入 `FTS5` 虚拟表；当前 1200 门课的 `LIKE` 完全够用 |
| D-6 | 无数据加密 | `securityLevel: S1`（应用私有） | 涉及学生个人信息时可用 `StoreConfig.encrypt` + `cryptoParam` 打开库加密 |
| D-7 | **导出表只有「考勤 1~5 / 课堂状态 1~5」十列 ⇒ 每门课最多导出 5 次点名**，第 6 次起的记录在库里但导不出 | 导出时只取最早 5 次并在提示里报出实际次数 | 属模板的既定格式（老师手里的表就这十列），不在库层设限；真要更多次点名，得先改模板格式 |

## 14. 小结

| 维度 | 结论 |
| :--- | :--- |
| 存储 | 单库 12 表，`RelationalStore`，无任何承载业务数据的 JSON 文件 |
| 原子性 | 所有跨表写操作走事务；`synchronous = FULL` |
| 完整性 | 外键 + 应用层显式级联，双保险；`class_info.class_id` 让班级改名不再丢名单 |
| 可查询 | 2 个视图 + 12 个索引，按周取数、冲突检测、人数对账、点名回填都是单条 SQL |
| 可演进 | `store.version` + 迁移器列表，新装与升级最终结构一致 |
| 迁移 | 旧 JSON 一次性单向导入并在成功后归档，幂等、可重入 |
