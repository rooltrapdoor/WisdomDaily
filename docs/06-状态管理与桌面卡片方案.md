## 1. 状态管理：v2.0 的 V2 形态**保持不变**【留档 · 未实施】

> **实施结论（2026-09-21）**：本节 v3.0 的"去掉 `@ObservedV2`、model 零装饰、页面整树 reload"**没有实施**。
> **当前真实形态**：
> - `model/*.ets` 7 个领域类**仍是** `@ObservedV2` + `@Trace`（字段级响应式保留）；
> - `pages/*.ets` 用 **`@ComponentV2` + `@Local`**（V2 页面状态），不是 `@State`；
> - 唯一部分采纳：**机主信息**（`owner_name` / `owner_staff_no`）**刻意不加 `@Trace`**（只在冷启动读、设置页写，无逐字段响应需求）。
>
> 因此以下 §1.1 ~ §1.4 降级为**备选方案留档**，供将来若真要"去 V2"时参考，**不代表当前实现**。

## 2. 桌面卡片（Service Widget）方案【已实施】

### 2.1 桌面卡片是什么

HarmonyOS 的服务卡片（Service Widget / Form）是**桌面级快入口**：卡片作为**独立 UI 实例**挂在桌面上。

> **怎么把卡片加到桌面（重要，HarmonyOS 5/6 改了交互）**：
> **双指捏合桌面 → 点击「卡片」进入服务中心 → 找到本应用 → 选 2\*2 或 2\*4 → 添加**。
> ⚠️ **不要指望"长按应用图标"**：官方支持页（consumer.huawei.com/cn/support/content/cn16018922）明确 —— HarmonyOS 5 起**不支持长按应用/上滑呼出服务卡片**；HarmonyOS 6 只支持**长按卡片**呼出更多卡片。本机真机（MIA-AL00 / HarmonyOS 6.1.0.135 / API 24）实测长按应用图标**没有卡片入口**，属系统行为，与卡片配置无关。

| 项 | 形态 |
| :--- | :--- |
| 进程归属 | 卡片跑在**卡片渲染进程**，与 `EntryAbility` 不同进程，由 `FormExtensionAbility` 承载 |
| 渲染 | ArkUI 声明式（与 `pages/` 同源），由 `form_config.json` 声明布局 |
| 数据 | 经 `FormBindingData` 注入；**不能**访问宿主 `EntryAbility` 实例，**不能**直接读数据库 |
| 更新 | `formProvider.updateForm(formId, binding)` 推送；系统另按 `form_config.json` 定时回调 `onUpdateForm` |

**关键结论**：卡片进程从 `FormExtensionAbility.onAddForm` 起步，**没有** `EntryAbility.onCreate` 那条链；且 `FormExtensionAbility` **空闲超过约 10 秒会被回收** —— 所以 `onAddForm` **必须同步返回**，把异步查库放到返回之后的 `updateForm` 里完成。

#### 2.1.1 API 20 卡片进程约束（实测）

| 约束 | 说明 |
| :--- | :--- |
| 禁用的 import | `multimedia.*` / `camera` / `media` / `backgroundTaskManager` / `particleAbility` 等在卡片进程不可用 |
| 允许的 import | `@kit.ArkData` 的 `relationalStore` / `preferences` **可用**（本项目取数依赖它） |
| `onAddForm` 必须同步返回 | 返回类型就是 `FormBindingData`；不能 `await` 查库后再 return |
| formId 来源 | `want.parameters[formInfo.FormParam.IDENTITY_KEY]`（字符串） |

### 2.2 卡片需求（实际只做 1 张，两种尺寸）

| 卡片名（`form_config.json` 的 `name`） | 尺寸 | 用途 | 数据源 |
| :--- | :--- | :--- | :--- |
| **`widget`** | **2\*2**（默认，150×150 vp） | **今天（开着「提醒第二天的课」时，22 点后为明天）未上完的课，最多 2 节**；窄卡版式（每节竖排两行：课程名 / 钟点 + 教室）；顶栏**不显示周数**、只留"还剩几节"的课程数徽标 | `repo.loadWeekLessons(semester, teacher, week)` 过滤 `weekday` → 滤掉已下课 → 按 `start_time` 取前 2 |
| **`widget`** | **2\*4**（2026-09-21 新增，316×150 vp —— **与 2\*2 同高、两倍宽**） | 同上（**也是 2 节**）；宽卡版式（横排两行，信息与课程块同口径 + 课程类型） | 同上，`rowsOfDimension()` 决定行数、`isWideDimension()` 决定版式 |

> 两种尺寸**共用同一张卡片与同一个卡片页**：`supportDimensions: ["2*2","2*4"]`。
> 卡片页跑在独立进程、**拿不到自己的尺寸**，所以"显示几行 / 用哪套版式"由提供方决定，
> 用绑定数据里的 `rowCount` 与 `cardWide` 传过去（详见 §2.3.5 / §2.3.9）。
>
> v3.0 规划的三张卡片（`today_lessons` / `current_lesson` / `week_summary`）**只落地了第一张**，且改名为 `widget`。另两张待排期。

### 2.3.3 `updateDuration` 与 `scheduledUpdateTime` 的**优先级陷阱**（重要）

官方规则（[配置 ArkTS 卡片的配置文件](https://developer.huawei.com/consumer/cn/doc/harmonyos-guides/arkts-ui-widget-configuration)）：

> `updateDuration` 参数**优先级高于** `scheduledUpdateTime`，两者同时配置时，**以 `updateDuration` 配置的刷新时间为准**。
> `updateDuration` 单位为 **30 分钟**，取值 N 表示刷新周期为 `30*N` 分钟。

**结论**：
- 本卡片用 **`updateDuration: 1`**（= 每 30 分钟刷新一次），是 API 允许的**最细周期**；
- **`scheduledUpdateTime` 已从配置中删除** —— 它本来只是"定点刷新"诉求，但会被 `updateDuration` 覆盖而**静默失效**，留着只会误导"我配了 22:00 定点刷新"；
- "**22 点后切换到次日课程**"**不是**靠定点刷新实现的，而是靠 `WidgetData` 每次刷新时用 `new Date()` **现算目标日**（见 §2.3.5）。刷新周期 30 分钟 ⇒ 跨过 22:00 后**至多 30 分钟**卡片翻到次日，属可接受精度；而且这个切换**只在「提醒第二天的课」开着时发生**（2026-09-23 起），开关关掉后卡片整天只说今天（见 §2.3.5 步骤 2）。

### 2.3.4 `EntryFormAbility` 生命周期（实际）

| 回调 | 时机 | 动作 |
| :--- | :--- | :--- |
| `onAddForm(want)` | 卡片被拖到桌面 | ① 从 `want` 取 formId **与尺寸**（`FormParam.DIMENSION_KEY`，只有这一次能拿到）→ `WidgetFormStore.saveForm`；② **同步** return `WidgetData.placeholder()`（"正在加载…"）；③ 同时起异步 `register → refresh(formId)` 覆盖 |
| `onUpdateForm(formId)` | 系统定时（每 30 分钟）/ 被 `updateForm` 触发 | `refresh(formId)` 重查重推 |
| `onRemoveForm(formId)` | 卡片被删 | `WidgetFormStore.removeFormId` 注销登记 |
| `onAcquireFormState(want)` | 系统查询卡片状态 | 返回 `FormState.READY` |

```ts
// entryformability/EntryFormAbility.ets（节选）
onAddForm(want: Want): formBindingData.FormBindingData {
  const formId: string = EntryFormAbility.formIdOf(want);
  const dimension: number = EntryFormAbility.dimensionOf(want);   // 2*2 → 2，2*4 → 3
  this.register(formId, dimension);                               // 先登记尺寸再刷新，顺序不能反
  return formBindingData.createFormBindingData(WidgetData.placeholder()); // 同步返回
}

private async refresh(formId: string): Promise<void> {
  const dimension = await WidgetFormStore.dimensionOf(this.context, formId);
  const rows = WidgetData.rowsOfDimension(dimension);             // 2*4 → 4 行，其余 → 2 行
  const data = await WidgetData.build(this.context, rows, false);  // false = 卡片进程只读，绝不写库
  await formProvider.updateForm(formId, data);
}
```

### 2.3.5 `WidgetData` 取数口径（实际）

`WidgetData.build(context, dimension, allowWrites = true)` → `compute(context, dimension, allowWrites)`：
传入的是**卡片尺寸**（`FormDimension`）而不是行数 —— 行数由 `rowsOfDimension()` 内部算（两种尺寸都是 2），
尺寸还额外决定**版式**（`isWideDimension()` → `cardWide`），见 §2.3.9。

1. `repo.init(context, allowWrites)` + `repo.loadWorkspace()`（拿当前指向的学期 / 教师）——
   卡片进程传 `allowWrites = false`：只打开连接读数据，播种 / 迁移 / 自愈一概不走（见 §2.4.1）；
2. `now = new Date()`；再读 `space.setting.notify_next_day`（=「我的 → 上课提醒」里的
   **「提醒第二天的课」**，也就是"提前一天晚上十点通知"）：**开着且 `now.getHours() >= 22` → 目标日 = 明天**，
   否则今天（`NEXT_DAY_HOUR = 22`）；**关掉开关则永远是今天** —— 这个切换存在的意义就是
   "今晚提前知道明天有课"，用户没要这条通知，就没有理由让卡片在晚上变成一份**没有标注**的次日课表
   （标题不写"明天"、列着明天的课，是最糟的中间态）；
3. 取标题：开关开着是 `今天|明天 · 周三`，关掉时**只有 `周三`**（永远都是今天的卡，标"今天"是废话）；
4. 找当前学期；**自算学期边界**（不调 `getWeekNumber` 的夹紧逻辑，否则"假期"会被夹到首/末周显示成有课）：早于第 1 周周一 → `学期还没开始`；晚于最后一天 → `学期已结束`；
5. `repo.loadWeekLessons(semester.id, teacherId, week)` → 过滤 `weekday === DateUtil.toDbWeekday(target.getDay())`；
6. **目标是「今天」时，再滤掉已经上完的课**：判据是「课程**结束**钟点 > 当前钟点」（正在上的那一节保留 —— 用户此刻最需要确认它在哪间教室）；作息模板查不到钟点时一律保留。22 点后目标是「明天」，整日不过滤。细节见 §2.3.8；
7. 按 `start_time`（并列再按 `end_time`）排序，**取前 `ROW_LIMIT` 条**（= 2，两种尺寸都一样）；
8. 每条映射成一行：课程名 + 班级名 + 课程色 + **行定位键 `rowNPeriod`（= `time_period_id`）**。
   内容按**卡片宽度**装两套（由 `isWideDimension()` 定，见 §2.3.9）：
   - 窄卡（2\*2）：`rowNCourse` = 课程名；`rowNMeta` = `HH:mm-HH:mm`（**窄卡不引用**，它用 `rowNStart` / `rowNEnd` 上下两行）；`rowNPlace` = `@教室` 与 `rowNPeople` = `45人`（**上下两行**）；`rowNClass` 装上但**窄卡不渲染**（放不下班级）；
   - 宽卡（2\*4）：`rowNCourse` = `课程名（课程类型）`；`rowNMeta` = `第N-M节 · HH:mm-HH:mm`；`rowNPlace` = `@教室 · N人`（人数取 `class_group.population`，为 0 时只剩教室）；`rowNPeople` 装着但不渲染（人数已并进 `rowNPlace`）；
   
   两套里教室都排在**不收缩**的那一段（`flexShrink(0)`），窄了先省略钟点；
9. 压成 `WidgetBinding`（**全基本类型**，卡片与提供方是两进程，复杂对象过不去），并写入整批课程的 `weekNo` / `weekday`（点课跳转的定位键）、版式标记 `cardWide`（1 = 宽卡）、**课程数徽标 `countText`**（今天 `剩 N 节` / 明天 `共 N 节`，当天一节不剩时为空串）与它的颜色 `countColor`（取自 `app_setting.today_color` —— 与应用里"今天"日期徽标同一个高亮色；卡片进程读不到设置，颜色只能随数据过来）；
10. `rowCount = min(剩余节数, ROW_LIMIT)` —— 卡片页据此渲染 1~2 行（卡片进程拿不到自身尺寸，只能用这个数）；**只剩一节**时卡片页在第二格放一个**空占位**（见 §2.3.9）。

空态文案分级：`还没有学期` / `学期还没开始` / `学期已结束` / `还没选择教师` /
`今天没课啦ヽ(*≧ω≦)ﾉ`（今天已经没有任何"还没上完"的课 —— 本来就没课、与全上完了共用这一句，
两者只在日志里区分）/ `明天没有课^-^`（22 点后目标日是明天）/
`数据忙，稍后自动刷新`（撞上跨进程锁且重试未果）/ `打开应用后可用`（库还没被应用初始化过）/
`数据读取失败` / 首帧 `正在加载…`。

**"只剩一节课"不算空态，只是"半空"**：课程块照常显示，下面那半格**留白**（`blankCell()`；2026-09-23 起 —— 原先补的是一句 `今天没课啦`，后来连同一句空态一起收窄成"只有真没课才说"，见 §2.3.9）。

### 2.3.6 卡片数据流

```
桌面添加卡片
   └─► EntryFormAbility.onAddForm(want)          ← 卡片进程
        ├─ WidgetFormStore.addFormId(context, formId)   （preferences 登记）
        ├─ return placeholder("正在加载…")               （同步，防被回收）
        └─ async refresh(formId)
              └─ WidgetData.build(context, rows, false)     （false = 卡片进程只读）
                   ├─ ScheduleRepository.init(ctx, false) + loadWorkspace  （读 wisdomdaily.db；不写）
                   ├─ 目标日 = (notify_next_day && hour>=22 ? 明天 : 今天)
                   ├─ loadWeekLessons(...) → 过滤 weekday → 取前 2
                   └─ formBindingData.createFormBindingData(binding)
              └─ formProvider.updateForm(formId, binding)
                    └─► WidgetCard 的 @LocalStorageProp('x') 被逐键更新（key 与 WidgetBinding 字段逐字一致）

应用切前台/后台
   └─► EntryAbility.onForeground / onBackground
        └─ WidgetUpdater.refreshAll(context)     ← 主进程
             └─ WidgetFormStore.listFormIds(context) → 逐个 formProvider.updateForm
                  （单个失败即 removeFormId，避免每次启动白试）
```

### 2.3.7 每行都留一个"不收缩"的锚点（教室不被压小）

卡片上每行都是**单行、不换行**（`maxLines(1)`）：一行里如果排了三样东西，最靠右的那样最先撑不住，
所以两套版式都遵守同一条规则：
**把"不能猜"的信息放在不收缩的那一段，让可推断的那一段先让步。**
「让步」的方式**一般不是省略号，而是缩小字号**（2026-09-22 改，见 §2.3.9 末段）——
被截成 `@综合实验…` 的教室等于没有，
所以钟点 / 教室 / 人数一律走 `minFontSize` + `maxFontSize` + `maxLines(1)` 的**自适应字号**。
**唯一的例外是窄卡课程名**（2026-09-22 晚二改）：固定 12pt、超长就在末尾收一个 `…` ——
课名有班级与课表可对照，是全卡唯一"截了还能猜"的信息；而缩字号会让同一张卡上两个课名
一大一小、看着像两个层级。见 §2.3.9 末段。

| 版式 | 行 | 可收缩段（`layoutWeight(1)` / `flexShrink(1)`） | 不收缩段（`flexShrink(0)`） |
| :--- | :--- | :--- | :--- |
| 窄卡 2\*2 | 第 2 行（第 1 行课程名独占） | 钟点（**竖排两行**：上 `08:00` / 下 `09:40`；`HorizontalAlign.Start` + `layoutWeight(1)`，**贴左**） | 教室 + 人数（**竖排两行**：上 `@A101` / 下 `45人`；`flexShrink(0)`） |
| 宽卡 2\*4 | 第 2 行 | `第N-M节 · 钟点` | `@教室 · N人` |

- 教室放在不收缩段：**教室无从推断**（钟点尚可由"第 N 节"大致推出、班级可由课程推出一半），
  所以先让步的永远是钟点（窄卡已经不放班级了；人数改挂在教室**下面一行**，不再与教室争同一行的宽度）。
- **两段两端对齐**（2026-09-22 晚二改；此前一度是"靠左紧挨"）：钟点**贴左**（左列 `HorizontalAlign.Start` + `layoutWeight(1)`，吃下剩余宽度）、教室与人数**贴右**（右列 `HorizontalAlign.End` + `flexShrink(0)`）。宽卡一直是这个排法（`layoutWeight(1)` 把 `@教室 · N人` 推到最右），窄卡原先照抄会在两段之间留出一大片空白、所以刻意改成了紧挨；现按用户要求与宽卡统一 —— 两张卡片看上去才是同一个设计。**左列不写 `layoutWeight(1)`、右列就顶不到右缘**，只写 `flexShrink` 是顶不过去的（`copy` 已写进 `widgetcheck.py` 断言）。**窄卡第二行的左段是"钟点上下两行"**（2026-09-22 晚，见 §2.3.9）：合体的 `10:55-12:35` 加上右边的 `@教室` 在 150 vp 里必被截成 `10:55-1…`（丢的正是"几点下课"），拆成上下两行后每行只有 5 个字符。
- **窄卡第二行是"左右各两行的四宫格"**【2026-09-22 晚】：左列钟点（上 = 开始 / 下 = 结束）、
  右列教室在上、**班级人数在下**。人数不与教室挤同一行 —— 150 vp 里挤进去必被吃掉半截，
  而"几个人"正是教室后面最容易丢的那个信息；挂在下面又与左列两行正好对称（§2.3.9）。
- 不收缩段为空（既没教室也没人数）时**整段不渲染**，免得 `Row` 的 `space` 白留一段间距。
- 人数取 `class_group.population`（登记人数），与课表页格子（`Index.ets` 的 `${lesson.population}人`）、课程详情（`${class_name} · ${population}人`）**同口径**；**为 0 时不显示**，避免出现"0人"。

### 2.3.8 卡片只显示两节、且只显示"还没上完"的课【2026-09-22】

两件事各自独立，但都为了同一个目的：**卡片上出现的每一行都必须是"当下仍然成立"的安排。**

#### (1) 行数从 4 收到 2

**先纠正一个前提**：按官方设计规范，小卡 2\*2 = **150×150 vp**，中卡 2\*4 = **316×150 vp** ——
两者**同高**，2\*4 只是两倍宽。"2\*4 更高、能放四节"是误解：早先给它排四行时高度没变、行数翻倍，
每组课程只剩一半高度，第二行"节次 · 钟点 + 教室 · 人数"这套 9pt 小字上下相压，
**读出来是错的**（内容串行 / 重叠），比少显示两节更糟。

现在 `WidgetData.ROW_LIMIT = 2`，`rowsOfDimension()` 对两种尺寸都返回 2；
**尺寸改为决定"版式"而不是"行数"**（见 §2.3.9）。

连带删除的是 **12 个恒空的契约字段**（`row3Course/Meta/Place/Class/Color/Period` 与 `row4*`），
`WidgetCard` 的 `@LocalStorageProp` 同批删掉，`WidgetBinding` 从 **30 键收到 18 键**
（2026-09-22 再加版式标记 `cardWide`、窄卡钟点的上下两半 `rowNStart` / `rowNEnd`、窄卡的人数 `rowNPeople`；**2026-09-23 删掉"只剩一节"的补齐文案 `moreText`（改成留白）、新增课程数徽标 `countText` 与它的颜色 `countColor`，共 **27 键**）。
留着不删的代价是"契约里有一半字段永远是空串"，下一轮改动的人会以为它们有效。

> `WidgetFormStore` 仍然登记卡片尺寸，但用途已从"算行数"变成"选版式"：
> `WidgetData.isWideDimension()` 按 `FormDimension.Dimension_2_4` 判宽窄，
> 装配成两组内容 + 一个 `cardWide` 标记推给卡片页，卡片页据此选 `courseRowNarrow` / `courseRowWide`。

#### (2) 按当前时间过滤掉已经上完的课

22 点前卡片标题常年是「今天 · X」。若把上午已经上完的课也摊在上面，
用户扫一眼看到的是**一份过期课表** —— 卡片就失去了"一眼知道接下来上什么"的意义。

| 判定 | 取值 | 理由 |
| :--- | :--- | :--- |
| 过滤对象 | 仅「今天」 | 22 点后目标日已是明天，整日都在未来 |
| 判据 | `课程结束钟点 > 当前钟点` | 用**结束**而不是开始：**正在上的那一节要留着** —— 用户恰恰在这时候最需要确认"这节课在哪间教室" |
| 钟点来源 | 当前学期绑定的作息模板（`ScheduleSlot`） | 与第二行展示的 `HH:mm` 同源，不会出现"显示的时间"和"过滤用的时间"不一致 |
| 查不到钟点 | **保留**（`endMinutesOf` 返回 -1） | 宁可多显示一节，也不能因为模板缺失把课静默吞掉 |

过滤后当天一节课都不剩时，空态文案是 **`今天没课啦ヽ(*≧ω≦)ﾉ`**（2026-09-22 改，窄卡颜文字另起一行）。
它同时覆盖"今天本来就没课"与"今天全上完了"两种成因 —— 对用户是同一件事（今天不用上课了），
卡片上再拆分只会让人怀疑数据；两者的区分留在 `WSD_WidgetData` 日志里，排查时能看出是哪一种。

**只剩一节课时不走这个空态，也不另行补话**：那半张卡的第二格**留白**（2026-09-23 改 —— 原先补的正是上面这句，但卡片上还挂着课、底下写"今天没课啦"自相矛盾）。于是《今天没课啦》**只在空态出现**：`noMoreText()` 的每一处调用都赋值给 `emptyText`，`widgetcheck.py` 逐行钉住这条。见 §2.3.9。

**边界**：卡片每 30 分钟才刷新一次（`updateDuration: 1`），所以"刚下课"到"卡片上消失"之间
最多有 30 分钟延迟，这是定时粒度的固有代价，不做处理。

### 2.3.9 两套版式：窄卡竖排两行、宽卡横排两行【2026-09-22】

同一个 `WidgetBinding`，按尺寸装成两组内容（`WidgetData.fillRow(binding, i, lesson, slots, wide)`），
卡片页只负责照单渲染（`courseRowNarrow` / `courseRowWide`）—— **数据加工一律留在提供方**，
卡片页跑在卡片进程里，既拿不到尺寸也不该做业务判断。

```
窄卡 2*2（150 vp 宽）                 宽卡 2*4（316 vp 宽，与 2*2 同高）
┌───────────────────────┐            ┌─────────────────────────────────────────────┐
│ 今天 · 周三  剩 2 节 ▣ │            │ 今天 · 周三               第 3 周  剩 2 节 ▣ │
│ ▏数字信号处理          │            │ ▏数字信号处理（理论）              计科2201 │
│ ▏08:00        @A101    │            │ ▏第1-2节 · 08:00-09:40        @A101 · 45人 │
│ ▏09:40          45人   │            │ ▏计算机网络（实验）                计科2202 │
│ ▏数据结构              │            │ ▏第3-4节 · 10:00-11:40        @B203 · 42人 │
│ ▏10:00        @B203    │            │                                             │
│ ▏11:40          42人   │            │                                             │
└───────────────────────┘            └─────────────────────────────────────────────┘
```

`▣` = 顶部右上角的**应用图标**（`ic_app`，14 vp）；`剩 2 节` 是**课程数徽标**（今天报"还剩几节"、明天报"当天共几节"，吃"今天"高亮色 —— 与应用里周次栏的日期徽标同色）；窄卡**不渲染周数**（150 vp 一行放不下四样），第二行是**左右各两行的四宫格** ——
左列钟点（上开始 / 下结束）、右列教室在上、**班级人数在下**。

| 项 | 窄卡（2\*2） | 宽卡（2\*4） | 为什么不同 |
| :--- | :--- | :--- | :--- |
| 行数（显示几节课） | 2 | 2 | 同高，行数必须一致（§2.3.8） |
| 每节课内部 | 竖排两行 | 横排两行 | 150 vp 宽横着一行最多放得下两样；316 vp 宽横排才成立 |
| 课程名 | 独占一行、**固定 12pt**，超长**末尾截断**（`…`） | 与班级同行、**≤13pt**（自适应） | 与班级同行两样都放不下、各被截去半截；窄卡独占一行后统一 12pt、长了在末尾收 `…` —— 缩字号会让同一张卡上两个课名一大一小，而课名有班级与课表可对照，截了还能猜 |
| 上课时间 | **钟点竖排两行**（上 = 开始、下 = 结束，各 10pt） | 显示"第N-M节 · 钟点"（一行） | 窄卡 150 vp 里"第1-2节 · "这 7 个字吃掉近半宽度；用户要知道的是"几点上" |
| 教室 | 显示（不收缩） | 显示（不收缩） | **两种版式都不能丢的两样之一**（另一样是课名）—— 教室无从推断 |
| 班级 | **不渲染** | 显示（与课程名同行） | 窄卡第二行要与教室并排，再塞班级就会把教室顶掉；班级可由课程推出一半 |
| 人数 | 显示（**挂在教室下面一行**；N=0 时不显示） | 显示（并进 `@教室 · N人`；N=0 时不显示） | 窄卡里与教室挤同一行必被吃掉半截，而"几个人"恰恰是教室后面最容易丢的信息；挂在下面又与左列"开始/结束"两行对称 |
| 课程类型 | 不显示 | 并进课程名 `（理论）` | 宽卡才放得下；也与应用内课程块的口径对齐（课程名 / 班级 / 教室 / 人数） |
| 顶部 | 标题 + **课程数徽标** + 应用图标 | 标题 + `第 N 周` + 课程数徽标 + 应用图标 | 窄卡 150 vp 一行放不下四样（标题 / 周数 / 课程数 / 图标），**砍掉周数、留课程数** —— "今天还剩几节"比"这一周第几周"要紧（2026-09-23）；徽标吃"今天"高亮色，是这一行唯一的强调元素 |

**窄卡为什么从三行收到两行**【2026-09-22】：原先第二行放钟点、第三行放 `班级 · @教室`，
看似信息更多，实际把三样东西压进 150 vp 的同一小格——**课名（12pt）与两行 9pt 小字上下挤在一起，
"班级"那一行又占掉了教室需要的宽度**。而桌面卡片真正要回答的只有"**这节课几点上、在哪上**"：
班级、节次、人数都能从课名推出，占了宽度反而把最不能猜的教室顶掉。收到两行后字号反而**升**了
（9pt → 10pt、11pt → 12pt），可读性比原来更好。

**窄卡第二行为什么把钟点拆成上下两行**【2026-09-22 晚】：真机上 `10:55-12:35  @1107` 被截成
`10:55-1…` —— 一格 150 vp 宽里，合体的钟点区间（11 个字符）加上 `@教室` 超出可用宽度约 20 vp，
而**被省略号吃掉的恰恰是"几点下课"**。改成"左边钟点上下排 / 右边教室"后：上面 `10:55`、
下面 `12:35` 各 5 个字符，宽度绰绰有余，教室也照旧完整（细节见 §2.3.7）。

**人数为什么另起一行，以及"不许出现省略号"**【2026-09-22 晚】：教室后面再接 ` · 45人` 时，
一是宽度又回到放不下（左边两行钟点 + 右边 `@1107 · 45人`），二是**真机上被吃掉的一定是排在最末的人数**。
所以人数**竖着挂在教室下面**（新增契约键 `rowNPeople`，与左边"开始/结束"两行对称）。
同时换掉降级方式：**钟点 / 教室 / 人数改用自适应字号**（`maxLines(1)` + `minFontSize` + `maxFontSize`），
不再用 `textOverflow(Ellipsis)` —— 宁可小一号也要让用户读全（这三样读了才知道，截了就没用了）。
**窄卡课程名是例外**（2026-09-22 晚二改）：固定 12pt + `maxLines(1)` + `textOverflow(Ellipsis)`，
超长在末尾截断 —— 见 §2.3.7 第一条。
注意 `heightAdaptivePolicy` **没有 `@form` 标记、卡片（form）里不可用**（查 SDK 的 `text.d.ts` 确认），
只能靠默认策略 `MAX_LINES_FIRST`：先缩字号，缩到下限仍放不下才截断。
顶部右上角另加**应用图标** `ic_app`（14 vp、`flexShrink(0)`），标题随之也改为自适应字号。

- 左右两段**两端对齐**（2026-09-22 晚二改；此前一度是"靠左紧挨"）：钟点贴左、教室与人数贴右 ——
  宽卡一直是这个排法（形成"左 = 节次钟点 / 右 = 教室人数"的对读关系），窄卡现与之统一，
  两张卡片看上去才是同一个设计。左列要写 `layoutWeight(1)`，否则右列顶不到右缘。
- 数据侧为此多给两格：`rowNStart`（开始钟点）/ `rowNEnd`（结束钟点），窄卡不再引用 `rowNMeta`
  （那是合体写法，留给宽卡）；与 `rowNClass` 同一条规矩 —— **停用不必删字段，删渲染引用即可**。
- 人数同理单列一格：`rowNPeople`（窄卡渲染在教室下面；宽卡把人数并进 `rowNPlace`，装着但不渲染）。
- 作息模板查不到钟点时，上半行退回节次（`第1-2节`）、下半行留空（那一行整行不渲染）。

**课程类型的写法**：`WidgetData` 里直接用 `lesson.course_type`（`v_lesson` 视图已带出，
取值 `理论` / `实验` / `实践`）拼成全角括号后缀 `课程名（实验）`。课名为空时先回落成"未命名课程"，
类型为空串时不加后缀（不留 `（）` 这种空壳）。

**卡片固定两格：只剩一节课时第二格留白**【2026-09-23 定；2026-09-22 那一版是补一句"没课啦"】：目标日只剩一节时，第一格照常显示课程块，第二格**什么都不写**。**格数与"还剩几节"无关**：只渲染一格时，那个课程块会被 `layoutWeight(1)` 拉满整张卡、又高又空，真机上看上去**像是数据没装配对**（2026-09-22 真机截图，见变更表第 19 条）。所以那一格**只留白、不取消**（`blankCell()` = 空 `Column` + `layoutWeight(1)`）—— 取消它比留白更糟。2026-09-22 晚曾在这格里补 `今天没课啦ヽ(*≧ω≦)ﾉ`（与空态同一句、字号 13pt、颜色 `#9CA3AF`），2026-09-23 按用户要求撤掉：**卡片上还挂着课，底下却写"今天没课啦"本来就自相矛盾**；那句话从此**只在空态出现**，`moreText` 也从契约里删干净（留着会让人以为它有值）。

窄卡 150 vp 放不下这一整行，按需求**在颜文字前换行**；换行由提供方写进数据（一个换行符），**不靠自动折行** —— 自动折行会随容器宽度变位置。

```
窄卡 · 只剩一节（2*2）            宽卡 · 只剩一节（2*4）
┌───────────────────────┐      ┌─────────────────────────────────────────────┐
│ 今天 · 周三    剩 1 节 │      │ 今天 · 周三              第 3 周  剩 1 节   │
│ ▏数字信号处理          │      │ ▏数字信号处理（理论）              计科2201 │
│ ▏08:00         @A101   │      │ ▏第1-2节 · 08:00-09:40        @A101 · 45人 │
│ ▏09:40                 │      │                                             │
│                       │      │                                             │
│      （留白）          │      │                       （留白）              │
│                       │      │                                             │
└───────────────────────┘      └─────────────────────────────────────────────┘
```

**这一格"给不给、给什么"的完整演变**：2026-09-22 早期只在"今天"的卡上补一句（22 点后标题写着「明天 · 周四」而那句话说的是"今天"）→ 同日晚改成**今天 / 明天的卡都给**（否则次日卡只剩一节时又会退回"一格被拉满"的形态，**格数跟着数据变才是问题的根源**）→ **2026-09-23 改成留白**：既然卡片上还挂着课，就不该出现"今天没课啦"；**要固定的始终是"两格"，不是"那句话"**。

**布局预算**（150 vp 高的卡）：卡片上下内边距取 **8**（规范建议 12）、头部与内容间距 5、
两格之间 4、**格内边距上下 4**。按这个预算：内容区 ≈ 134 − 头部 18~19.5 − 5 = 109.5，
**固定两格**各约 53，减去格内边距还剩 ≈ 45；窄卡一格是"课程名 12pt + 两行 10pt 钟点"
（≈17 + 26，`lineHeight` 定死 13，免得随字体度量浮）—— 共 ≈ 43，**刚好站得住**。
格内边距正是为此从 5 收到 4（多出来的那一行钟点吃掉这 2 vp）。
**所有纵向余量都从内边距里抠（规范 12 → 8），一点也没动字号** ——
10pt 是这张卡片可读性的下限，再小就该改为少显示一节课（而不是继续缩字）。
**真机上若仍出现纵向裁切，先继续调这几个内边距。**

### 2.4 数据层桥接（卡片进程如何读到库）

| 问题 | 实际解法 |
| :--- | :--- |
| `ScheduleRepository.init(context)` 要 `common.Context` | ✅ **无需改动** —— `FormExtensionAbility.context` 也是 `common.Context` |
| 卡片进程读 `wisdomdaily.db` | ✅ `ScheduleDb` 用 `context.databaseDir` 定位，两进程看**同一文件** |
| 卡片进程写库 | ❌ **不做** —— 卡片只读；写动作仍由 `EntryAbility` 触发 |
| 枚举已添加的 formId | ⚠️ `formProvider` **无此接口** → 自建 `WidgetFormStore`（见 §2.5） |

#### 2.4.1 跨进程共用一个 RDB：`14800024`（2026-09-22 真机缺陷 + 修法）

> 上表"卡片进程读库 ✅ WAL 并发读无问题"、"写库 ❌ 不做"两句在 2026-09-21 是**意图**，
> 而实现里并不是这样：卡片刷新走的 `ScheduleRepository.init()` → `doInit()` 会**无条件开一个写事务**
> （`SeedData.seedIfEmpty` + `ensureRow` + `repairPointers` + `repairDanglingClassGroups`，
> 哪怕一行都不用改）。于是卡片每 30 分钟刷一次＝每 30 分钟对库写一次。

真机现象：应用冷启动时整页空白，红条 + 弹窗写着

```text
课表加载失败: code=14800024, message=SQLite: The database file is locked.
```

**这不是数据坏了**：14800024 就是 SQLite 的 `SQLITE_BUSY`，两个进程有一个正持写锁。
`getRdbStore` 的 `@throws` 清单里**没有**这个码，说明失败发生在某条语句执行时，不是"打不开库"。

修法落在这三处（完整分析见 `docs/04` §12.3.2 (22)）：

| 位置 | 改动 |
| :--- | :--- |
| `EntryFormAbility.refresh()` | `WidgetData.build(context, rows, false)` → 卡片进程只读：不执行 PRAGMA、跳过播种 / 导入 / 自愈（`ScheduleDb.init(context, false)`） |
| `ScheduleRepository.doInit()` | 先用只读语句探一遍（`isSeeded` / `needsRepair` / `listDanglingGroups`），确认确有坏行才开写事务 → 稳态启动**零写** |
| `DbLock`（新增） | 遇 14800024 / 14800025 指数退避重试（80→**800ms**，最多 5 次）；语句级在 `StoreExecutor`，事务级在 `runInTransaction`（**提交阶段不重试**） |

**顺带纠正一个 API 用法**：不要把 `StoreConfig.isReadOnly` 当"只读连接"用 —— WAL 模式下
**读连接同样要能写 `-wal` / `-shm`**，真开成只读反而打不开库。这里的 `allowWrites` 限制的是
"应用层主动写"，连接权限不变。

**卡片上的失败文案分三种**（`WidgetData.build`）：锁占用 → `数据忙，稍后自动刷新`；
库还没被应用初始化过 → `打开应用后可用`；其它 → `数据读取失败`。

### 2.5 刷新三条路径（实际）

| # | 路径 | 触发者 | 进程 | 覆盖场景 |
| --- | --- | --- | --- | --- |
| 1 | `onAddForm` | 用户添加卡片 | 卡片进程 | 首帧 + 立刻查一次 |
| 2 | `onUpdateForm` | 系统定时（`updateDuration:1`，30 分钟） | 卡片进程 | 长时间不打开应用也会更新（含 22 点切次日） |
| 3 | `WidgetUpdater.refreshAll` | `EntryAbility.onForeground` / `onBackground` | 主进程 | "刚改完课表，回桌面立刻是新的" |

> **2026-09-22 补充（进程边界）**：路径 1 / 2 跑在**卡片进程**，一律用**只读用途**初始化
> （`ScheduleRepository.init(context, false)`）—— 不执行 PRAGMA、不播种、不自愈；
> 路径 3 跑在**应用进程**，正常初始化（该播种就播种）。原因见 §2.4.1。

**为什么需要 formId 登记簿**：路径 3 在主进程执行，而主进程**拿不到**"本应用当前有哪些卡片"——`formProvider` 只提供"按 formId 更新"，**没有**"列出全部 formId"的接口。于是由卡片进程在 `onAddForm`/`onRemoveForm` 时把 formId 写进 `preferences`（`schedule_widget` 库、`form_ids` 键，逗号分隔字符串），主进程只读。

> **为什么不用写路径通知**（v3.0 计划的 `notifyForms`）：把推送塞进 `ScheduleRepository` 的每个写方法会让数据层反向依赖 UI 层；改由 `EntryAbility` 生命周期兜住，既有"改完即新"的观感，又保持数据层零侵入。

### 2.6 交互：点击卡片上的课 → 应用内打开该课详情【已实施 · 2026-09-21】

v3.0 规划的是 `postCardAction({action:'message', params:{message:'open_main'}})` + `onFormEvent` 只"跳回主页"。
实际实现比它更有用：**点哪一节课就打开哪一节课的详情**，链路如下 ——

```
WidgetCard 某一行 onClick
   └─► postCardAction(this, { action: 'router', abilityName: 'EntryAbility',
                              params: { wsdWeek, wsdWeekday, wsdPeriod } })      ← 卡片进程（只允许在点击回调里触发）
        └─► 应用冷启动：EntryAbility.onCreate(want)     ← 应用没在运行
            应用在后台：EntryAbility.onNewWant(want)    ← 单实例 launchType 不会重走 onCreate，必须单独接
               └─► WidgetLaunch.request(want.parameters)  （模块级待办 + 2 分钟有效期）
                    └─► Index.onPageShow → consumeCardLaunch()
                         ├─ await 首次刷新（冷启动走 initRefresh，避免两次并发刷新把周次覆盖回去）
                         ├─ switchWeek(周次)                    ← 卡片可能显示"明天"，跨周也要跳对
                         ├─ 按 time_period_id 找回该课次（当前教师找不到 → 扫本学期其它教师）
                         └─ openLessonSheet(lesson)              ← 与点课表课块完全一致的详情半模态
```

四个实现要点（都已在 docs/04 §12.3.2 第 20 点第 11 条留档）：

| 要点 | 做法 | 为什么 |
| :--- | :--- | :--- |
| 传什么定位键 | **周次 + `time_period_id`**（另带 `weekday` 供校验） | 22 点后卡片显示的是"明天"，可能跨到下一周，只传 id 找不到；两者组合才能唯一定位一课次 |
| 不写 `bundleName` | `params` 里只有 `abilityName: 'EntryAbility'` | 不写默认就是本应用，省掉一处与 `app.json5` 重复的包名（改名时最容易漏的就是这种硬编码） |
| 跨进程怎么交接 | 新增 `widget/WidgetLaunch.ets`：`request()` 写入、`take()` 取走（取一次即清空、**2 分钟过期**） | 首页是 `@ComponentV2`，不读 AppStorage V1 的键；且请求不需要可观察性。过期是为了"用户正停在全屏编辑页"时不会几分钟后被突然弹出的面板吓到 |
| params 落在哪 | `want.parameters` 直接是键值对，**或** `want.parameters.params` 是 JSON 字符串 —— 两种都兼容 | 文档示例与部分版本的实测行为不一致，兼容两种最省事 |

补充行为：**时间表编辑页**（`TemplateEdit`）在 `onPageShow` 里若发现有待办且**没有未保存改动**，会自动退回首页让请求生效（有改动时以用户编辑优先，请求 2 分钟后自行过期）；课程详情找到后若该课已被删除，则提示「已不在课表中」而**不是静默无反应**。

#### 2.6.1 空态卡片也有落点：点它进应用看课表【2026-09-22】

卡片一节课都没有时，点它进应用看课表 —— 走的还是 §2.6 那条通道，**区别只在"带不带 `wsdPeriod`"**：

| 点击对象 | `params` | 应用侧落点 |
| :--- | :--- | :--- |
| 某一行课程 | `wsdWeek` + `wsdWeekday` + `wsdPeriod` | 切到该周 + 打开该课详情半模态 |
| **空态卡片（整张都可点）** | 只有 `wsdWeek` + `wsdWeekday` | 收起开着的面板 → 切回「首页」页签（`TabsController.changeIndex(0)`）→ 课表落到**卡片显示的那一周** |
| 环境类空态（`还没有学期` / `学期还没开始|已结束` / `还没选择教师`） | 两个键都是 `0` | **不登记待办**，只把应用拉起来 —— 课表页本身就是这几种情况的提示页 |

三点值得记住：

- **整张卡可点，不是只有那句文案**：`onClick` 挂在外层 `Column` 并判 `rowCount === 0`（挂内层会出现"点卡片上半部分没反应"）；有课时这个判断直接跳过，各行跳转仍归各行自己的 `onClick`。
- **周次要"算得出就写"**：`WidgetData` 原先写的是"有课才写 `weekNo` / `weekday`"，空态点进去就只会落到"今天所在周"，而卡片上写的可能是明天（周日 22 点后就是下一周）。现在一算出周次就写，两种跳转共用同一对定位键。
- **页签只能靠控制器切**：用户可能把应用停在「我的」那一屏，而卡片说的是"今天没课" —— 点进去当然是看课表。`Tabs` 的 `index` 是**初值、不是可观察状态**，要用 `TabsController.changeIndex(0)`；`activeTabIndex` 再同步一份，因为"本来就停在第 0 页"时不会触发 `onChange`，导航栏选中态得靠它保持一致。

`WidgetLaunch.request` 的判据随之放宽：原先 `week <= 0 || period <= 0` 一律丢弃，现在**两个都缺**才丢弃 —— `periodId = 0` 是一种合法意图（"只看课表"），契约写在 `WidgetOpenRequest.periodId` 的注释上。

## 2.8 上课提醒【2026-09-22 · 已实施】

> 「我的 → 上课提醒」两个开关 + 一个提前量输入框。提醒本身**不在应用里跑定时器**，
> 而是登记到系统的"后台代理提醒"上。

### 2.8.1 为什么用系统后台代理提醒，而不是应用内定时器

`setTimeout` / `workScheduler` 这类手段都要求应用**还活着**。而上课提醒的场景恰恰相反：
用户合上应用去上课，应用被回收、被冻结才是常态。系统级代理提醒（`reminderAgentManager`）
由系统闹钟托管，**应用不运行、被清理掉也能准时弹** —— 这是这个功能唯一可用的实现路径。

| 候选 | 结论 |
| :--- | :--- |
| `setTimeout` / 页面内计时 | ✗ 应用一退后台就没了 |
| 长时任务 / 后台任务 | ✗ 需常驻前台通知（"正在运行"常驻条），为一个上课提醒挂个常驻通知不成比例 |
| **`reminderAgentManager`** | ✅ 系统托管、应用不运行也能弹；用 `ReminderRequestCalendar` 精确指定年月日时分 |

### 2.8.2 两条提醒规则

| 开关 | 名称 | 触发条件 | 触发时刻 |
| :--- | :--- | :--- | :--- |
| ① | 提醒第二天的课 | **次日有课** | 当天 **22:00** |
| ② | 是否提前提醒 | 当天 / 次日每节课，且不满足"被上一节吃掉"的例外 | 上课前 **N 分钟**（N 默认 **20**，可改，收在 [1, 120]） |

两个开关独立，互不依赖；都关闭时调度器只做一次"清空旧提醒"。

### 2.8.3 「这节课之前 N 分钟另一节课才结束，就不提醒」

提前提醒的触发时刻是 `上课钟点 − N`。如果这个时刻**还落在另一节课里**，
弹出来只会打扰正在上课的人 —— 所以这条不提醒。

判据实现为：**同一天存在另一节课，其结束钟点 ≥ 提醒时刻**（等价于"两节课之间的间隔 ≤ N 分钟"）。

| 例（N = 20） | 上一节结束 | 本节开始 | 提醒时刻 | 结论 |
| :--- | :--- | :--- | :--- | :--- |
| 连排 | 09:40 | 10:00 | 09:40 | ❌ 不提醒（恰好撞上上一节下课） |
| 课间 10 分钟 | 09:40 | 09:50 | 09:30 | ❌ 不提醒（09:30 时上一节还在上） |
| 课间 30 分钟 | 09:40 | 10:10 | 09:50 | ✅ 提醒（此时已在课间，离上课还有 20 分钟） |
| 当天第一节 | — | 08:00 | 07:40 | ✅ 提醒 |

- 「另一节课」取**当天、当前教师**的全部课程（与应用主视角同口径）；
- N 就是用户在输入框里设的那个值，不是写死的 20 —— 默认值下与需求描述完全一致；
- 判断在**登记时**完成：不满足条件的课根本不会产生提醒条目，因此不存在"到点才决定要不要弹"的时序问题。

### 2.8.4 调度模型：每次全清重建

`LessonReminder.sync(context, force)` 的流程：

1. **清点 → `cancelAllReminders()` → 再清点**：先量一次 `getValidReminders()`，把上一批清掉，再量一次。
   两次的差就是"清不掉的额度"（系统把**已弹出、但用户没点关闭**的提醒也算作有效，见 §2.8.5），
   日志里的 `提醒额度清点：清理前 N 条 / 清理后 M 条` 是唯一能看出额度去向的地方；
2. 两个开关都关 → 到此为止（剩下的就是"清理"）；
3. 读当前学期 / 教师 / 作息模板，算出**「今天起 4 天」**每天的课（按周缓存，避免重复查库）；
4. **收集**两类提醒到一份清单，**按触发时刻升序**排队，再逐条登记 ——
   额度紧张（上限 30 条）时先保住"马上就要响"的那几条；
5. 撞上 `1700002`（额度满）→ **立即停手**并熔断 10 分钟：额度满了之后每条登记都必然失败，
   继续发只是把日志刷成一片红。熔断期内**连清理都不做**（清了也登记不回来）。

**为什么不留增量、每次全清重建**：课表随时会被编辑（改时间、删课、换教室），提醒内容里带着这些信息。
增量维护一旦哪一步出错，就会留下一条**永远不会消失**的旧提醒 ——
用户看不到它、也没有删它的入口，只能卸载重装。全清重建把状态**只留在课表里**，提醒表永远是可再生快照。

代价与边界（必须同时记住）：

- `cancelAllReminders()` 取消的是**本应用的全部提醒**。以后若再加别的提醒功能，要么共用一个调度器，
  要么改用 `groupId` 分组清理；
- 扫描窗口是 **4 天**而不是 3 天：22 点那条要判断"**次日**有没有课"，
  "后天 22:00"这一档必须能看到第 4 天的课表，否则它永远不会被登记；
- 提前提醒只登记 **今天 + 明天**（`AHEAD_DAYS = 2`），后天及以后的等明天的同步再补；
- 同步有 **20 秒节流**（`SYNC_THROTTLE_MS`）：`refresh()` 触发很频繁（切周、编辑返回都会跑），
  不节流会反复"清空 + 重发十几条"；开关变更走 `force = true` 绕过节流，拨一下立刻生效；
- 失败时把节流计时归零，下一次刷新可以立刻重试；
- **额度满后熔断 10 分钟**（`QUOTA_COOLDOWN_MS`）：期间不登记、也不清理，
  到期后由下一次 `sync` 自己重试（见 §2.8.5）。

### 2.8.5 额度：30 条有效提醒与「关闭」按钮

系统对代理提醒有**个数限制**，而"有效"的算法很反直觉 —— 官方《代理提醒》指南原文：

> 单个普通应用**有效/未过期**的提醒数量不超过 30 个（API ≤ 25；API ≥ 26 为 64 个）。
> 当到达设置的提醒时间点时，通知中心会弹出相应提醒。**若未点击提醒上的关闭/CLOSE 按钮，
> 则代理提醒是有效/未过期的。**

也就是说：**一条提醒弹出之后并不会自动"用完"，只要用户没点那个关闭按钮，它就一直占着额度。**
2026-09-22 的真机日志因此长成这样（`WSD_LessonReminder`，三分钟内十几条）：

    登记提醒 #2200 失败：{"code":1700002,"message":"The number of reminders exceeds the limit."}
    登记提醒 #2201 失败：{"code":1700002,"message":"The number of reminders exceeds the limit."}

**整段没有一条成功行** —— 连每次同步的第一条都失败，说明额度在同步之前就已经满了。
而当时的 `publish()` 从来**没配过 `actionButton`**（官方样例是必带的）：用户连能点的地方都没有，
额度只进不出，攒到 30 之后每节课的提前提醒都登记不上。

四条规矩（都进了 `remindercheck.py`）：

| # | 规矩 | 为什么 |
| :-- | :--- | :--- |
| 1 | 每条提醒都带 `actionButton`（`ACTION_BUTTON_TYPE_CLOSE`） | 这是额度**唯一**的出口；不配就永远释放不了 |
| 2 | `sync` 在 `cancelAllReminders()` **前后各** `getValidReminders()` 清点一次 | 唯一看出额度被谁占着的地方（清不掉的就是"已弹出"的那些） |
| 3 | 撞 `1700002` → 熔断 10 分钟 + 本批立即停手 | 额度满了之后每条登记都必然失败，继续发只是刷屏 |
| 4 | 收集完按**触发时刻升序**登记 | 额度紧时先保住"马上就要响"的那几条 |

**熔断期连清理都不做**：清了也登记不回来，只会把用户仅剩的提醒弄没 ——
所以那句"熔断期直接返回"必须写在 `cancelAll()` **之前**。顺序反了不报编译错，只会"提醒凭空消失"，
`remindercheck.py` 用**行号顺序**钉住了它。

排查提醒问题时**先量权限，别先猜**：

    $ hdc shell atm dump -d -p ohos.permission.PUBLISH_AGENT_REMINDER   # 权限定义（SYSTEM_GRANT）
    $ hdc shell atm dump -t -b com.wxz.wisdomdaily                 # 授予状态
    { "permissionName": "ohos.permission.PUBLISH_AGENT_REMINDER", "grantStatus": 0 }
    # grantStatus 0 = 已授予、-1 = 拒绝（同一份 dump 里 WRITE_MEDIA 正是 -1）

## 2.9 签到（点名）与考勤导出【2026-09-22 · 已实施】

### 2.9.1 状态模型：一个 `@ObservedV2` 类 + 一份快照

点名页的状态只有两层，刻意做得极薄（页面 `CheckIn.ets`，1 395 行）：

| 层 | 形态 | 为什么 |
| :--- | :--- | :--- |
| 每行标记 | `@ObservedV2 class SignInMark`（`@Trace student_id / status / grade / score`） | 手势改的是**某一个学生**的 `status`；靠 `@Trace` 逐字段观察，只有那一行重绘，不必每次改动都重建整份列表（本工程 `model/` 层保留 V2 装饰器的既定形态，见 §1） |
| 脏标记 | `baseline`（真正入库的值的快照）与 `refreshDirty()` 的 `snapshot()` 内容比对 | 沿用全屏时间表编辑页的口径（`docs/04` §12.3.2 第 14 点）："改了又改回原样 = 没改"；`@Builder` 按值传参不参与观察，所以判脏**不能靠回调触发过没有** |

页面参数（`periodId` / `weekNo` / `classId` / `mode` / `randomCount` / `themeColor` …）经 `router.pushUrl` 传基本类型；
`aboutToAppear` 里读一次 `display` 拿屏宽高（圆环浮层与手势阈值都要用），再 `load()`。

`load()` = `loadRoster(classId)` + `loadAttendance(periodId, weekNo)` 两次读，然后把已有签到**回填**到 `marks`：
库里有的行按 `student_id` 命中，库里没有的就是 `AttendStatus.NONE`（"没点过名"在库里不占行）。

`mode = 'random'` 时在加载后立刻 `rollTargets()`：**Fisher–Yates 洗牌**取前 `randomCount` 个下标作为点名对象。
抽出来的 N 人只是"这次点谁"，不预设出勤结论 —— 老师照旧逐人滑。

### 2.9.2 手势矩阵

三种标记动作全部落在同一行上，靠手势形态区分（不用长按菜单，也不用勾选框）：

| 动作 | 手势组合 | 判据 | 结果 |
| :--- | :--- | :--- | :--- |
| 旷课 | `PanGesture(PanDirection.Horizontal)` | 松手时 `globalX` 位移 ≤ −阈值 | `status = absent`，行上出 `×` |
| 请假 | 同上（反方向） | 松手时 `globalX` 位移 ≥ +阈值 | `status = leave`，行上出 `⊕` |
| 撤销 | 同一方向**再滑一次** | 该行已是该方向的状态 | 回到 `NONE`（手势误触的退路） |
| 评等级 | `GestureGroup(Parallel, 水平 Pan, GestureGroup(Sequence, LongPressGesture(320ms), 任意方向 Pan))` | 先按住 320ms，再把手指拖到圆环上；环上实时高亮所在格 | `status = present` + `grade` + `score`（松手落档；落在**取消格**或环心死区里=这次长按作废，**不改动**原标记） |
| 进单人视图 | **列表最底下那个按钮**的 `onClick` | **不挂在行上** —— 一行已有 3 个手势，再加"轻点"会和长按的 320 ms 判定抢手指 | `viewMode = 'one'`，停在第一位还没点名的学生 |

- **位移一律用 `event.fingerList[0].globalX / globalY`**（按下时记初值、结束时相减）。
  `offsetX` 的单位随场景在 vp / px 之间变，同一段位移在不同设备上判定结果不同。
- **外并行、内串行**：外层 `Parallel` 让"长按拖动"与"短滑"互不抢手势；内层 `Sequence` 保证
  必须是"先按住、再拖动"才出圆环 —— 否则随手一划就会弹浮层。
- **长按之后是任意方向**（`PanDirection.All`）：圆环是整圈，上/下/左/右都对应某一格。
  代价是同一个触摸里"往右拖"也会被行上的水平 `PanGesture` 看见，于是加一道 `ringTouch` 闸门 ——
  **它在 `TouchType.Down` 清零，而不是在抬手时清**：抬手时两个 Pan 的 `onActionEnd` 谁先回调，
  不由我们决定，靠顺序去判就是赌运气。
- **浮层不吃手势**：圆环浮层挂在 `Stack` 上层并设 `HitTestMode.None`，命中判断交给页面自己算角度，
  避免"手指落在浮层上就丢失后续 move 事件"。
- **长按期间只操作被选中的那一行**：其余行压一层 `#00000059` 遮罩并把 `hitTestBehavior` 设成
  `HitTestMode.Block`（挡住它们自己的手势），列表同时 `enableScrollInteraction(false)`；
  被长按的那一行加边框与投影浮起来。老师的手指就是那一根，不该有第二行同时响应。

### 2.9.3 圆环选等级：1/3 是取消，剩下的均分给五档

```
                  ┌── 取消（120° = 1/3 圆）──┐
           ①(90~95)                       ⑤(65~71)
                ·                        ·          ← 六个格沿圆环排（半径 = 固定 96 vp）
           ②(85~89)   ·   ③(80~84)   ·   ④(72~79)
                   （环心 = 长按点，手指从环心拖出去选格）
```

- 几何全在 `model/Attendance.ets`：`RING_CANCEL_SPAN = 120`、`RING_GRADE_SPAN = 48`，
  两者满足 `120 + 48 × 5 = 360`；基准是**正上方 0°、顺时针为正**，于是
  **正上 = 取消、正左 = 1 档、正下 = 3 档、正右 = 5 档** —— 与上一版半圆同一套手感。
- 判定（`ringSectorOf()`）、画点角度（`ringGradeAngle()`）、点的偏移（`ringOffsetOf()`）是**三个纯函数**，
  页面只做"环心 + 偏移"：画出来的点落在哪一格，手指滑到那个点就必须选中哪一格。
- **死区 30 vp**：手指没离开环心这么远就不选中任何格，抬手等于什么都没做（长按误触不会记档）。
- 「取消」= **这次长按作废**，不改动这个学生原有的标记（要清标记走"再滑一次同方向"那条路）。
- 为什么不用"找最近的圆点"：六个点在小屏上可能相距不到 40 vp，指尖一点抖动就会在两格之间跳；
  而角度在半径方向上没有分辨问题（远离环心后角度分辨率反而更高）。
- **分档区间写在 `model/Attendance.ets` 一处**（`GRADE_BANDS`），导出侧只引用不重抄：
  1 → 90~95、2 → 85~89、3 → 80~84、4 → 72~79、5 → 65~71，**上端取开**避免 90 分既算 1 又算 2。
- **分数在选中那一刻随机生成并落库**（`randomScoreOfGrade`），不是导出时现算 —— 否则同一份记录
  导两次分数不同，老师没法对账。

### 2.9.4 落库与导出（两种口径）

点右上角「完成」时：收集 `marked()` 的 `SignInMark` → `AttendanceRow[]` → `saveAttendance(periodId, weekNo, rows)`；
仓储层在一个事务里 `replaceSession`（**先清本次课、再整批写**）。返回键 `onBackPress` 在脏时弹「放弃修改？」。

导出入口在**班级名册**（不是点名页）：`loadClassAttendance(classId)` 取全班的签到行，
按 `(week_no, weekday, start_time)` 排序**一次点名定一列**（最多 5 列，与模板的十列对应），
然后由"导出班级名单"弹窗二选一：

| 口径 | 考勤列（4~8） | 课堂状态列（9~13） |
| :--- | :--- | :--- |
| **原表**（`scored = false`） | 旷课 `×`、请假 `⊕`，**出勤留空** | 等级 `1~5` |
| **算分后**（`scored = true`） | `√`（只要是 1~5 的考勤）/ `×` / `⊕` | 等级换算出的**分数** |

两种口径共用 `rosterRows(withStudents, scored)` 一个拼表函数（表结构、合并单元格、边框三处完全共用），
只换"往格子里填什么"；没点过名的学生留空，两种口径都不写。

### 2.9.6 只读的「查看本节课程情况」

用户在签到面板里看到的三个选项：**随机指定人数点名** / **全部点名** / **查看本节课程情况**。
最后一项是**只读看板**，与点名页刻意不同：

| 维度 | 点名页（`pages/CheckIn.ets`） | 查看本节课程情况（就地展开） |
| :--- | :--- | :--- |
| 落点 | 全屏页（`router.pushUrl`） | 课程详情 sheet 内一层（`sheetAction = 'checkinView'`） |
| 写库 | 点「完成」整批替换 | **完全不写库**，纯读 |
| 手势 | 左滑 / 右滑 / 长按下滑 | 无（列表只作展示） |
| 取数 | `loadRoster` + `loadAttendance` + 回填 `SignInMark` | `loadRoster` + `loadAttendance` → 压成只读行 |
| 内容 | 可编辑的行 | 四格计数 + 已点名进度 + 已评级平均分 + 逐人列表 |

几个实现要点：

- **列表顺序取名单的学号自然序**（`compareNo`），不是签到表的写入顺序 —— 后者是"老师滑动的先后"。
- **面板主体封顶 280 vp、整块滚动**：课程详情 sheet 是 `FIT_CONTENT` 且外层没有兜底滚动，
  面板总高 ≈ 头部 68 + 课程信息块（最满 228）+ 本面板，手机可用高约 700 vp。
  统计与逐人列表收在**一个** `Scroll` 里一起滚（`constraintSize({ maxHeight })`），
  「返回」放在 Scroll 外面 —— 只给列表封顶时总高仍随人数按行高累加，最满那一档会被切掉。
- **平均分只统计评过级的人**：没点名 / 旷课 / 请假都没有分数，把它们当 0 分平均会把
  "全班考勤良好"算成四五十分，比不显示更容易误导。
- **`back` 逐层退回**：从看板返回退回**签到面板**（`sheetAction === 'checkinView' ? 'checkin' : 'none'`），
  而不是一步跳回课程详情 —— 老师多半是"看完接着点名"。

> 与卡片 / 提醒的关系：签到**不参与**卡片取数，也不触发提醒重建 —— 它只写 `attendance`，
> 不动 `course` / `time_period` / `period_week`，因此课表、卡片、提醒的既有链路完全不受影响。

| R-12 | 提醒只登记"今天起 4 天"（提前提醒只有今天 + 明天）。用户连续多天不开应用 → 更远的提醒不会被补登 | 可接受：①「次日有课」那条 22 点提醒本身就是把用户拉回应用的最强动机；②用户打开应用即自动重建。若将来要覆盖长假，改成 `repeatDays` 周期性提醒即可 |
| R-13 | 用户拒绝通知授权后，提醒**仍会被登记**但弹不出来 | 首次拨开开关时弹系统授权框；被拒后立刻给一句文字提示（指向「设置 → 通知和状态栏」）。不做循环弹框 |
| R-14 | 「上课前 N 分钟」只按**当前教师**的当天课程判断间隔；若用户在另一位教师名下也有同时段的课，判据不覆盖 | 与应用主视角（当前教师）一致；跨教师连排是极边缘的场景，暂不处理 |
| R-15 | 提醒额度（30 条）由**系统**掌管，且包含"已弹出但用户没点关闭"的那些；应用只能清点、不能扩容 | 已按 §2.8.5 四条规矩把损耗降到最低（每条带关闭按钮 / 清点 / 熔断 / 排队）。用户长期不点关闭时额度仍会被缓慢吃掉 —— 那时应用表现为"提醒不再新增、但也不再刷错误日志"。**这是系统策略、不是缺陷**；真要减少占用只能少登记（例如砍掉"后天 22:00"那一档，代价见 R-12） |

## 6. 小结

| 改动面 | v3.0 计划 | 实际落地 |
| --- | --- | --- |
| 状态层 | 6 model 去装饰器 + 1 page 改 reload | **未改**（保留 V2；仅机主字段不加 `@Trace`） |
| 卡片扩展 | Ability + form_config + 卡片页 + 快照器 + 写后通知 | **Ability + form_config + 卡片页 + `WidgetData` + `WidgetFormStore` + `WidgetUpdater` + `WidgetLaunch`**（多登记簿与跳转交接各一个） |
