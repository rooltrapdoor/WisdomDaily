## 1. 设计原则

| 编号 | 原则 | 落地要求 |
| :--- | :--- | :--- |
| P1 | **页面不碰 SQL** | 页面组件禁止 import `@kit.ArkData`，禁止出现任何表名、列名、SQL 片段；一切数据经 `ScheduleRepository` |
| P2 | **模型不依赖存储** | `model/` 下的领域类不得 import `relationalStore` / `relationalStore.RdbStore` / `ValuesBucket`；保证可被单元测试直接构造 |
| P3 | **单一数据源** | 表结构只在 `TableSchema.ets` 定义一次；每张表只有一个 DAO；SQL 不复制粘贴 |
| P4 | **显式映射** | `ResultSet` ↔ 领域对象必须经过 `RsReader` 读取器与 `fromRow()/toRow()`，不做隐式类型转换 |
| P5 | **失败可降级** | 任何一次读取失败都返回安全默认值 + 记日志，不允许因数据异常导致应用无法进入首页 |
| P6 | **状态驱动视图** | 视图刷新只能由响应式状态变更触发，禁止手动"重新渲染整页" |
| P7 | **写入事务化** | 任何跨表写入必须包在一个事务里（`runInTransaction`），要么全成功要么全回滚 |
| P8 | **密钥稳定** | 业务主键（`course_id` / `class_id`）为不可变 UUID，重命名不改主键 |
| P9 | **资源国际化** | 所有面向用户的文案走 `$string` 资源，禁止在 `.ets` 中硬编码中文 |
| P10 | **连接唯一** | 全应用只有 `ScheduleDb` 一个单例持有 `RdbStore`，其余代码只能拿 `DbExecutor` |

## 2. 总体架构

采用**单体分层架构（Layered Monolith）**。本应用无服务端，全部逻辑运行于单进程内的 UIAbility 中，因此不引入微服务、网关等分布式复杂度。

```
┌───────────────────────────────────────────────────────────────────────┐
│  ① 宿主层 Host                                                        │
│     EntryAbility（生命周期 / 数据库初始化）· EntryBackupAbility（备份）  │
├───────────────────────────────────────────────────────────────────────┤
│  ② 表现层 Presentation                                                │
│     ArkUI 页面（5 路由页 + 待办面板）/ 半模态 / 桌面卡片页 WidgetCard    │
├───────────────────────────────────────────────────────────────────────┤
│  ③ 状态层 State                                                       │
│     V2 响应式状态（@ObservedV2 / @Trace / @Provider / @Local）          │
├───────────────────────────────────────────────────────────────────────┤
│  ④ 业务编排层 Repository                                              │
│     ScheduleRepository（课表）· TodoRepository（待办）：事务 · 组装 · 编排 │
├───────────────────────────────────────────────────────────────────────┤
│  ⑤ 数据访问层 DAO                                                     │
│     单表 SQL · ResultSet 行映射 · 只返回 *Row · 不判业务                │
├───────────────────────────────────────────────────────────────────────┤
│  ⑥ 数据库基础设施 DB                                                   │
│     ScheduleDb（单例连接）· TableSchema（DDL）· DbMigrations · DbExecutor│
├───────────────────────────────────────────────────────────────────────┤
│  ⑦ 领域模型层 Domain                                                  │
│     SemesterCourses → Teacher / Course → ClassGroup → TimePeriod       │
│     TodoTask / TodoSubtask（独立支流，不挂学期）                          │
├───────────────────────────────────────────────────────────────────────┤
│  ⑧ 存储与系统能力 Platform                                             │
│     RelationalStore（SQLite 库文件）· Preferences · AbilityKit …        │
└───────────────────────────────────────────────────────────────────────┘
        ▲ 依赖方向：自上而下单向；唯一例外是 ④⑤ 依赖 ⑦ 的领域类型（不是反向）
```

**跨层约束**

| 编号 | 铁律 | 校验方式 |
| :--- | :--- | :--- |
| R1 | 只有 `ScheduleDb` 能持有 `RdbStore`；其他层只能拿 `DbExecutor` | 全局搜索 `getStore()` 调用点应仅限 `ScheduleDb` 内部与 `ScheduleRepository.stats/backup/restore` |
| R2 | 页面/组件层不得出现 `@kit.ArkData`、表名常量、SQL 关键字 | 搜索 `pages/` 下的 `SELECT`/`INSERT`/`UPDATE`/`DELETE` 应为 0 命中 |
| R3 | DAO 只返回 `*Row`（`model/Rows.ets`），不得返回领域对象 | DAO 的返回类型标注 |
| R4 | 领域模型 `model/*.ets` 不得 import 任何存储 API | 搜索 `model/` 下的 `relationalStore` 应为 0 命中 |
| R5 | 事务边界只能由 Repository 决定，DAO 不得自行 `beginTransaction` | 搜索 `dao/` 下的 `beginTransaction` 应为 0 命中 |
| R6 | 领域模型不得持有文件路径或存储句柄（旧版 `getClassPath()` 之类已删除） | 搜索 `model/` 下的 `Path`/`filesDir` 应为 0 命中 |

> 这六条铁律在 v1.0 中因"领域层 import DAO、DAO 反向依赖领域类"而无法成立（v1.0 的 ARCH-01 循环依赖）；改用 DAO/Row 分离 + `DbExecutor` 注入后，依赖图变成严格的单向 DAG。

### 3.2 `TableSchema.ets` —— 表结构唯一真源

所有 DDL 常量集中在一个文件，任何地方需要表名/视图名/列清单都从这里取，杜绝字符串散落。

| 导出常量 | 内容 | 数量 |
| :--- | :--- | :--- |
| `DB_NAME` | `'wisdomdaily.db'` | — |
| `DB_VERSION` | `7` | — |
| `Tables` | 14 张表的表名常量对象 | 14 |
| `Views` | `V_LESSON='v_lesson'`、`V_TEMPLATE_STAT='v_template_stat'` | 2 |
| `DDL_TABLES` | 建表语句数组（含 CHECK / UNIQUE / FOREIGN KEY） | 14 |
| `DDL_VIEWS` | 视图定义 | 2 |
| `DDL_INDEXES` | 索引定义 | 14 |
| `PRAGMA_SETUP` | `foreign_keys` / `journal_mode` / `synchronous` | 3 |

**14 张表**：`schedule_template`、`schedule_slot`、`semester`、`teacher`、`app_setting`、`course`、`class_info`、`class_group`、`time_period`、`period_week`、`student`、`attendance`（v6，签到记录）、`todo_task` / `todo_subtask`（v7，待办两表，**不挂任何外键**）。

字段级定义与约束矩阵见 [02-数据库设计 §4](02-数据库设计.md#4-表结构详细定义)，本节不重复。

### 3.3 模块依赖关系

```
宿主(EntryAbility)
  └─依赖→ Repository ──┬─依赖→ Service(ConflictDetector / LessonReminder)
                       ├─依赖→ DAO ×11 ──依赖→ DbExecutor/DbSupport
                       ├─依赖→ ScheduleDb（连接/事务/迁移）
                       └─依赖→ model/*（领域类型与 *Row）

页面(Index / CourseEdit / TemplateEdit / CheckIn / Todo / TodoEdit)
  └─依赖→ Repository（只此一条数据入口）

卡片(EntryFormAbility / WidgetCard)
  └─依赖→ WidgetData → 只读 ScheduleDb（卡片进程绝不写库）

DAO ──依赖→ TableSchema（表名）、Rows（行类型）、DbExecutor（执行器）
model/* ──依赖→ nothing（纯数据 + 纯函数）
db/* ──依赖→ @kit.ArkData（唯一允许 import relationalStore 的目录）
```

**关键：`ScheduleRepository` / `TodoRepository` 是页面的唯一数据入口。** 页面不持有 `DbExecutor`、不 import DAO。这样做的收益是：事务边界、级联删除顺序、种子/迁移/旧数据导入全部收口在一处，页面层不需要理解任何存储细节。

## 4. 技术选型

| 领域 | 选型 | 理由 | 备选与否决原因 |
| :--- | :--- | :--- | :--- |
| 语言 | **ArkTS**（严格类型子集） | API 20 官方首选；编译期类型检查减少运行时错误 | 否决 JS：失去静态类型与性能优化 |
| UI 框架 | **ArkUI 声明式** | 与 V2 状态管理原生协同，是 NEXT 的唯一长期方向 | 否决类 Web / 声明式 old API |
| 状态管理 | **状态管理 V2**（`@ObservedV2` / `@Trace` / `@ComponentV2`） | 字段级精确追踪，深嵌套对象改动也能精准刷新 | 否决 V1：深层嵌套需手动 `@ObjectLink` 层层传递 |
| 页面路由 | **`router` 页面路由**（`@kit.ArkUI` 的 `router.pushUrl` / `getParams` / `back`） | 页面数少（5 个全屏页）、无分栏诉求；API 20 的 `router` 仍是稳定的页面路由入口，写法最省、`main_pages.json` 注册即用 | 否决 `Navigation` + `NavPathStack`：本项目没有"左列表右详情"的分栏场景，引入 NavDestination 只会把 5 个页面全部改写一遍（见 ADR-10） |
| **持久化** | **`RelationalStore`（`@kit.ArkData`）SQLite** | 强类型、约束内建、索引加速、事务保证原子性、可视图/聚合统计；单文件便于系统级备份 | 否决 **沙箱 JSON 文档**：非原子写、无约束、无索引、全量重写、对象图与存储强耦合（详见 [02 §1](02-数据库设计.md#1-存储选型决策)）；否决 **Preferences**：仅键值、不支持列表与联表 |
| 数据库形态 | **单库单文件**（`wisdomdaily.db`）+ WAL | 一次连接、一次打开，避免多库跨事务；WAL 提升并发读写体验 | 否决"每学期一个库"：跨学期聚合需 ATTACH，且事务无法跨库 |
| 安全等级 | `SecurityLevel.S1` | 课表为一般业务数据，S1 满足沙箱隔离要求且性能最优 | S2/S3 引入额外加密开销，无必要 |
| SQL 组织 | **DAO 手写 SQL + 参数绑定** | 表少、SQL 简单，手写可控且便于优化；避免 ORM 带来的 ArkTS 元数据兼容问题 | 否决三方 ORM：与 `@ObservedV2` 装饰器元数据冲突，且引入包体积 |
| 序列化 | **`ValuesBucket` 显式构造 + `RsReader` 显式读取** | 类型确定、无隐式转换；与领域对象的 `fromRow`/`toRow` 一一对应 | 否决反射/装饰器自动映射 |
| 日志 | **hilog（PerformanceAnalysisKit）+ `Logger.ets` 统一出口** | domain `0x0A01` 可独立过滤；`%{public}s` 显式标注防截断 | 否决纯 `console.log`：正式包不可控 |
| 颜色选择 | 自研 HSV 拾色器（页面层，后续实现） | 与截图需求一致；避免三方库与 API 20 的兼容风险 | 否决 `color-picker` 三方库：实际未被参考工程使用 |
| 测试 | **hypium + hamock** | 官方测试框架 | — |
| 三方依赖 | **无**（`oh-package.json5` 的 `dependencies` 为空） | 本次所有能力均由系统 Kit 提供 | 已移除 `class-transformer`、`reflect-metadata`、`color-picker` 等未生效依赖（v1.0 的 ARCH-10） |

## 5. 接口约定

### 5.1 领域对象统一契约

所有领域类必须实现以下协议：

| 方法 | 签名 | 作用 |
| :--- | :--- | :--- |
| `fromRow` | `≪static≫ (row: XxxRow): Xxx` | **从数据库行还原领域对象**（替代 v1.0 的 `constructor(obj?: Interface)`） |
| `toRow` | `(): XxxRow` | **转为数据库行**，供 DAO 写入 |
| `clone` | `(): Xxx` | 深拷贝，用于"复制课程/班级"与防止外部引用污染 |
| `toString` | `(): string` | 调试日志输出 |

**约定细则**

- `fromRow` 必须对每个可空字段给出显式默认值（如 `row.course_score ?? null`），保证任何缺失列都有合法值。
- 数组字段一律深拷贝（`.map(x => x.clone())`），**禁止直接赋值引用**。
- `clone()` 内部走 `fromRow(toRow())`，保证与持久化路径一致。
- 领域类**不再有** `getValue()`（那是为 JSON 序列化服务的，已随 JSON 方案移除）。

### 5.2 数据访问层契约 — `DbExecutor`

把 `RdbStore` 与 `Transaction` 的同形方法收口为一个接口，使 DAO 只写一次即可同时服务两种场景。

```ts
export interface DbExecutor {
  insert(table: string, values: relationalStore.ValuesBucket): Promise<number>;
  batchInsert(table: string, values: Array<relationalStore.ValuesBucket>): Promise<number>;
  update(values: relationalStore.ValuesBucket, predicates: relationalStore.RdbPredicates): Promise<number>;
  delete(predicates: relationalStore.RdbPredicates): Promise<number>;
  querySql(sql: string, bindArgs: Array<relationalStore.ValueType>): Promise<relationalStore.ResultSet>;
  executeSql(sql: string, bindArgs: Array<relationalStore.ValueType>): Promise<void>;
}
```

| 实现 | 构造方式 | 语义 |
| :--- | :--- | :--- |
| `StoreExecutor` | `new StoreExecutor(store)` | 单条语句自动提交。用于纯读与单表写 |
| `TxExecutor` | `new TxExecutor(tx)` | 语句并入外层事务，随事务回滚。用于 Repository 的事务体内 |

**这是本方案最重要的设计决策**：如果没有这层抽象，每个 DAO 方法都要写成两份（一份收 `RdbStore`、一份收 `Transaction`），或者让 DAO 感知"当前是否在事务中"。有了它，`SemesterDao.deleteCascade(tx, id)` 与 `SemesterDao.count(store)` 共用同一份实现。

### 5.3 读取器契约 — `RsReader`

`ResultSet` 的 `getString/getLong/getDouble` 在列不存在或值为 NULL 时行为不一致（会抛错或返回 `null`），直接散布在 DAO 里极易出错。统一封装为类型确定的读取器：

| 方法 | 签名 | 语义 |
| :--- | :--- | :--- |
| `has` | `(col): boolean` | 列是否存在于结果集 |
| `isNull` | `(col): boolean` | 值是否为 NULL |
| `str` | `(col, fallback=''): string` | NULL/缺失 → `fallback` |
| `optStr` | `(col): string \| undefined` | NULL/缺失 → `undefined` |
| `num` | `(col, fallback=0): number` | 整数；NULL/缺失 → `fallback` |
| `optNum` | `(col): number \| undefined` | NULL/缺失 → `undefined` |
| `real` | `(col, fallback=0): number` | 浮点；NULL/缺失 → `fallback` |
| `optReal` | `(col): number \| null` | **真 NULL 语义**（用于 `course_score`） |
| `bool` | `(col, fallback=false): boolean` | 0/非0 → `false`/`true` |

`optReal` 是 v1.0 `?? 2` 修 bug 的落点：`course_score` 未填时读出来就是 `null`，而不是"2 学分"。

| 对象 | 规范 | 示例 |
| :--- | :--- | :--- |

## 6. 关键设计决策（ADR）

### ADR-01：用状态管理 V2 而非 V1

- **背景**：课表数据是"学期 → 教师 → 课程 → 班级 → 时间段"五层嵌套，编辑页修改的是最内层字段。
- **决策**：全局采用 `@ComponentV2` + `@ObservedV2` / `@Trace`。
- **理由**：`@Trace` 能追踪到嵌套对象的**具体字段**，改动最内层的 `class_room` 也只刷新依赖该字段的组件；V1 的 `@Observed` 只观测第一层属性，深层改动需要链条式 `@ObjectLink` 传递，在五层嵌套下不可维护。
- **代价**：V2 与部分 V1 修饰符不能混用，混用会静默失效，需在代码评审中把守。

### ADR-02：编辑即事务提交，不再有"内存优先 + 兜底落盘"

- **背景**：v1.0 采用"编辑页改内存副本 → 返回时合并 → 生命周期兜底落盘"，导致三个问题：进程被杀丢数据、非原子写损坏文件、脏标记语义脆弱（失败仍清零）。
- **决策**：**所有写操作以"用户点保存"为界，当场在事务中提交到 SQLite**，返回成功后才更新内存状态；不再有 `isCourseChange` / `isScheduleChange` 这类脏标记，也不在生命周期回调里做兜底保存。
- **理由**：SQLite 的事务本身提供原子性与持久性（`synchronous = FULL` + WAL），进程被杀只可能丢"用户还没点保存的那一步输入"，而这一步本来就该丢。这比"依赖四个生命周期回调都恰好执行"可靠得多。
- **代价**：写操作变成异步，页面需要处理 `await` 与失败提示；对高频小改动（如拖动周数滑块）需做防抖，不能每动一下就写库。

### ADR-03：`DbExecutor` 抽象收口"连接 / 事务"二元场景

- **背景**：DAO 既要能在无事务的单表操作中使用，又要能并入 Repository 的多表事务。
- **决策**：定义 `DbExecutor` 接口，`StoreExecutor` 与 `TxExecutor` 两个实现；DAO 方法首参一律 `DbExecutor`。
- **理由**：见 §5.2。若无此抽象，DAO 要么重复实现两遍，要么让 DAO 反向依赖连接状态，破坏分层。
- **代价**：每次调用多一层间接寻址（可忽略）；开发者需要理解"传 `store` 还是传 `tx`"的区别，需在 Repository 中严格区分。

### ADR-04：关系型数据库（RelationalStore）作为唯一持久化方案

- **决策**：见 [02-数据库设计 §1](02-数据库设计.md#1-存储选型决策)。
- **补充**：JSON 仅保留一个用途 —— **旧数据一次性导入**（`LegacyJsonImporter`），导入成功后归档到 `legacy_json_backup/`，此后不再读写。`resources/rawfile/` 刻意留空，不再需要 JSON 种子。

### ADR-05：级联删除"双保险"

- **背景**：SQLite 的外键约束默认关闭，且**是按连接生效的**；`RelationalStore` 使用内部连接池，无法保证每条语句都跑在开启了 `foreign_keys` 的连接上。
- **决策**：① 每条连接建立后执行 `PRAGMA foreign_keys = ON`；② **同时**在 DAO 层实现显式级联删除（`deleteCascade`），删除顺序与依赖方向严格一致：`period_week → time_period → class_group → course → teacher|semester`。
- **理由**：只依赖外键 → 在连接池下可能失效，产生孤儿行；只依赖应用层 → 一旦有遗漏就永久脏数据。双保险的代价只是多几条 `DELETE`。
- **代价**：`deleteCascade` 必须手写且不能漏表。为降低风险，`class_group → class_info` 的关系**刻意使用 `ON DELETE RESTRICT`**：宁可删除失败报错，也不能静默删掉班级名单。

### ADR-06：冷启动用"直查 + 内存拼装"，按周取数才用视图

- **背景**：`v_lesson` 视图把时间段按周展开，适合"取某周课表"；但若用它来组装整学期对象图，5 个学期 × 12 节 × 7 天 × 20 周的展开会让行数膨胀数十倍。
- **决策**：整学期加载走**6 条直查**（`semester`+模板 / `teacher` / `course` / `class_group` / `class_info` / `time_period`+`period_week`）+ 内存 Map 逐层拼装；`loadWeekLessons` 走 `v_lesson`。
- **理由**：冷启动是延迟最敏感的路径，6 条索引覆盖的查询在毫秒级；按周查询则天然带 `week_no` 条件，视图能显著简化 SQL。
- **代价**：两条读路径并存，需在文档中明确各自适用场景（详见 [05 §4.1](05-系统架构与数据流.md)）。

### ADR-07：`period_week` 拆表，把周次语义下推到 SQL

- **背景**：v1.0 把周次存成 `number[]`，冲突检测只能把全部时间段读进内存再逐个求交。
- **决策**：周次拆为独立表 `period_week(period_id, week_no)`，并在 `week_no` 上建索引。
- **理由**：冲突检测可以直接写 `AND pw.week_no IN (1,2,3,…)`，让 SQLite 用索引先筛掉不冲突的候选集，只有候选集里的少数几行才需要做节次区间相交判断。
- **代价**：读写周次都要多一次子表操作；`replaceWeeks` 采用"先删后插"的简单策略（周次集合小，批量插入足够快）。

### ADR-08：视图 `citation_count` 取代冗余计数字段

- **背景**：v1.0 中 `SemesterSchedule.citation_count` 是手工维护的冗余字段，任何绑定/解绑路径漏改都会漂移。
- **决策**：改为视图 `v_template_stat` 实时 `COUNT(*)`。
- **理由**：模板数量是个位数，实时统计成本可忽略；不漂移比省一次聚合更重要。
- **代价**：`citation_count` 从模型属性变成只读字段（`ScheduleTemplate.citation_count` 由 `fromRow` 填入，不可通过 `toRow` 写回）。

### ADR-09：不可变业务主键取代"按名称关联"

- **背景**：v1.0 用学期名作文件名、用班级名作名单文件名，重命名即丢关联。
- **决策**：`course_id`（UUID）与 `class_id`（UUID）为业务主键，`id INTEGER PRIMARY KEY AUTOINCREMENT` 为代理键；名称只是可变属性。
- **理由**：重命名变成一次 `UPDATE`，不再需要"改名文件 + 改引用 + 改设置"三步编排（v1.0 的 DEF-02 高危缺陷从根上消失）。
- **代价**：所有关联都要通过主键，不能再用名称做联表的"偷懒"写法；需要在 `class_info` 上对 `name` 加唯一约束以免产生同名班级。

### ADR-10：页面路由用 `router`，不引入 `Navigation` + `NavPathStack`（2026-10-19 定案）

- **背景**：折叠屏/平板下曾期望"左列表右详情"的分栏体验，一度规划 `Navigation(NavPathStack)`。
- **实测结论**：全项目只有 5 个全屏页（`CourseEdit` / `TemplateEdit` / `CheckIn` / `TodoEdit` 及主页），
  且都是"从主页进去、办完事回来"的单向流程，没有并列列表与详情共存的场景；
  项目最终统一使用 `@kit.ArkUI` 的 **`router.pushUrl` / `router.getParams` / `router.back`**，
  页面在 `entry/src/main/resources/base/profile/main_pages.json` 注册。
- **决策**：**继续用 `router`**；不新增 `Navigation` 容器，也不把已有页面改造成 `NavDestination`。
  页面参数只传**主键**（`semesterId` / `taskId` / `periodId` / `weekNo` 等），不传对象引用。
- **理由**：① 现有交互没有分栏诉求，`Navigation` 带来的自适应能力用不上；② `router` 的写法更短，
  取参处统一 `router.getParams() as Record<string, Object>` + 逐键判 `undefined` + 校 `NaN`；
  ③ 半模态（`bindSheet`）与 `AlertDialog` 属于页内视图切换，本来就不该进路由栈。
- **代价**：宽屏下没有自动分栏；"返回并携带结果"要靠 `router.back({ url, params })` 或重新查库。

### ADR-11：时间轴与网格共用同一节次数据源

- **背景**：左侧时间轴与右侧课程网格必须严格行对齐，否则课程块会错位。
- **决策**：两者都从同一份 `schedule_slot`（节次槽）与固定行高常量推导坐标，**行高不使用百分比或弹性布局**。
- **理由**：弹性布局在小数像素下会产生 1px 累积误差，导致越往下的课程块偏移越明显。
- **代价**：手机与折叠屏需分别配置合适的行高常量。

### ADR-12：到点提醒交给系统代理提醒，而不是应用内定时器

- **背景**：需求「第二天有课则 22:00 提醒、当天有课则提前 N 分钟提醒」。
  直觉做法是在应用里起 `setTimeout` / 长时任务。
- **决策**：用系统**后台代理提醒**（`@kit.BackgroundTasksKit` 的 `reminderAgentManager`），
  以 `ReminderRequestCalendar` 指定精确的年月日时分；提醒**条目不入库**，每次按课表全清重建。
- **理由**：
  1. 应用内定时器要求应用还活着，而"上课提醒"发生的时刻，应用**一定不在前台**（用户在上课）；
  2. 代理提醒由系统闹钟托管，应用被回收、被冻结也能准时弹；
  3. 不持久化提醒条目 = 不存在"课表改了、提醒没跟上"的一致性问题，库里只有课表一个真源。
- **代价**：`cancelAllReminders()` 是**应用级**的（会清掉本应用全部提醒），
  所以将来新增任何提醒功能都必须并入同一个调度器，或改用 `groupId` 分组清理；
  另外只登记"今天起 4 天"，依赖用户每隔几天打开一次应用来续期（详见 `docs/06` §2.8.4 / R-12）。

## 7. 横向设计

### 7.1 异常处理策略

采用**分层收敛**：底层只记日志不抛异常，上层决定降级或提示。

| 层 | 策略 |
| :--- | :--- |
| ② 表现层 | `try/catch` 包裹 Repository 调用，失败用 Toast / 弹窗提示；不阻塞页面进入 |
| ③ 状态层 | 不接受异常，只接受"有效数据" |
| ④ Repository | 捕获存储异常 → `describeError()` → 返回 `boolean`/结果对象；事务内异常向上抛给 `runInTransaction` 触发回滚 |
| ⑤ DAO | 不捕获（除 `finally` 关游标）；SQL 错误由 Repository 统一处理 |
| ⑥ DB 基础设施 | `init` 失败记 `error` 并置不可用标志；`runInTransaction` 保证 `rollback` 与 `commit` 互斥 |

**分级**

| 级别 | 场景 | 处理 |
| :--- | :--- | :--- |
| Fatal | 数据库无法打开（磁盘满、沙箱不可写） | 提示"存储不可用"并转入只读模式，禁止一切写操作 |
| Recoverable | 表结构缺失（迁移中断） | `hasTable()` 检测 → 重建缺失的表/视图/索引 |
| Degradable | 单字段非法（颜色格式、周次越界） | 写入前归一化/夹紧（`normalizeColor` / `normalizeWeeks`），静默修正并记日志 |
| Info | 查询返回 0 行（属正常首启） | 走种子流程，**不视为错误**（v1.0 在此处误用 `console.error`，已改为 `info`） |

**游标（`ResultSet`）的生命周期铁律**：所有 DAO 的 `querySql` 结果必须 `try/finally { rs.close() }`，禁止把 `ResultSet` 向上层传递。全局静态校验 0 处遗漏。

### 7.2 日志策略

| 场景 | 工具 | 说明 |
| :--- | :--- | :--- |
| 统一出口 | `Logger.ets` | 封装 `hilog`，domain `0x0A01`，tag 前缀 `WSD_`（WisdomDaily），四级 `debug/info/warn/error` |
| 关键流程 | `WSD_Db` / `WSD_Repo` | 建库、迁移、事务提交/回滚、级联删除行数、种子与导入结果 |
| 正常路径 | `info` | 例如"数据库已存在，跳过建表" |
| 失败 | `error` | 必须携带 **操作类型 + 表名/主键 + 错误码 + message**（`errText()` 统一格式化） |

**v1.0 的 JSON 日志截断问题已消失**：不再需要分段打印超长 JSON（`LogUtil` 已删除）。

### 7.3 相较 v1.0 的架构问题修正对照

v1.0 列出了 10 项已知架构问题（ARCH-01~ARCH-10）。改用关系库后，其中 7 项从根上消失，3 项转化为新的约束。

| v1.0 编号 | 问题 | v2.0 状态 |

### 7.4 安全与隐私设计

| 项 | 设计 |
| :--- | :--- |
| 权限 | 仅声明 `ohos.permission.WRITE_MEDIA`（导出到媒体库），**不申请网络权限**，从权限层面保证数据不出设备 |
| 数据隔离 | 数据库文件位于应用私有沙箱 `databaseDir`，其他应用无法访问；`SecurityLevel.S1` |
| 注入防护 | 所有 SQL 一律使用参数绑定（`?` 占位 + `bindArgs`），**禁止字符串拼接用户输入**；表名/列名来自 `TableSchema` 常量而非用户输入 |
| 导出确认 | 导出必须由用户主动触发并经系统文件选择器确认，不静默外发 |
| 输入校验 | 名称类字段走 `cleanName()` 去除首尾空白与控制字符；颜色走 `normalizeColor()`；周次走 `normalizeWeeks()` 夹紧 |
| 敏感信息 | 教师电话、学生电话属个人信息，仅在本地展示；`student.telephone` 为 **TEXT** 类型（修正 v1.0 用 `number` 丢前导 0 的问题），导出时提示用户注意 |
| 完整性 | `PRAGMA foreign_keys = ON` + 应用层显式级联（ADR-05）；`app_setting` 存真实主键，启动时 `repairPointers()` 修正悬空指针 |

### 7.5 多端与折叠屏适配

| 形态 | 策略 |
| :--- | :--- |
| 手机竖屏 | 单栏 + `router` 页面栈；课表列宽 = 屏幕宽 × 7 等分 |
| 折叠屏展开 / 平板 | 当前**未做分栏**：仍旧单栏，仅按屏宽放大列宽与字号；如后续要做"左列表右详情"，再评估 `Navigation`（见 ADR-10 的取舍） |

## 10. 概要设计小结

本应用是**单进程、无服务端、离线优先**的本地工具类应用，架构的核心矛盾不在"分布式一致性"，而在**"编辑体验的顺滑"与"进程随时可能被杀"之间的平衡**。

v1.0 用"内存优先 + 四时机兜底落盘"来平衡，代价是把数据安全押在"四个生命周期回调恰好都执行"上，并因此引入了非原子写、脏标记语义错误、领域层循环依赖等一串问题。

v2.0 选择**把平衡点前移到数据库**：

1. **分层保清晰** —— 七层单向依赖 + 六条铁律，页面经 `ScheduleRepository` / `TodoRepository` 两个门面取数，UI 不碰 SQL、模型不碰存储。
2. **事务保安全** —— 编辑即事务提交，SQLite 的原子性与持久性取代脆弱的兜底落盘；级联删除双保险 + 启动指针自愈。
3. **主键保正确** —— 不可变 `course_id`/`class_id` 让重命名不再需要多步编排；`v_lesson` / `v_template_stat` 让派生数据不再手工维护。
4. **抽象保简洁** —— `DbExecutor` 让 DAO 写一次即同时服务连接与事务；`RsReader` 让 `ResultSet` 的类型陷阱集中在一处。

详细的类结构、算法与实现约束见 [04-详细设计.md](04-详细设计.md)；架构图与端到端数据流见 [05-系统架构与数据流.md](05-系统架构与数据流.md)；表结构与 SQL 见 [02-数据库设计.md](02-数据库设计.md)。
