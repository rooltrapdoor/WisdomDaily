## 1. 系统定位

一个**单机、单用户、离线可用**的院校教师课表工具：教师维护自己的多个学期课表，
按周查看，管理班级名单与作息时间，数据全部保存在设备内置的关系型数据库中。

| 特征 | 取值 | 对架构的影响 |
| :--- | :--- | :--- |
| 部署形态 | 单 HAP，无服务端 | 无需网络层、无需鉴权、无并发冲突 |
| 数据规模 | 每学期约 3 MB 上限 | 单库完全够用，不需要分库分表 |
| 主要风险 | **进程被系统回收** | 写入必须事务化、即时落库，不留"待保存"窗口 |
| 访问模式 | 读多写少，读集中在冷启动与切周 | 冷启动做一次全量装配，之后增量刷新 |
| 依赖能力 | 文件、关系库、系统备份、文件选择器 | 全部为系统内置 Kit，无三方运行时依赖 |

## 2. 系统架构

### 2.1 分层职责

系统采用**七层单向依赖**架构。相较上一版（JSON 文档存储），最大变化是把原来的
"文件存储工具层"替换为 **RelationalStore + DAO + Repository 三层**。

```
┌───────────────────────────────────────────────────────────────────────────────┐
│ ⑦ 宿主与生命周期层                                                             │
│   EntryAbility · EntryBackupAbility · EntryFormAbility · WidgetLaunch            │
│   职责：开库初始化、窗口装载、退出时释放连接                                     │
├───────────────────────────────────────────────────────────────────────────────┤
│ ⑥ 页面与组件层                                                                 │
│   pages/Index（课表/待办/我的）· CourseEdit · TemplateEdit · CheckIn · TodoEdit  │
│   pages/Todo（面板组件）· widget/pages/WidgetCard + 管理 sheet 内各子视图        │
│   职责：布局与交互、状态绑定的宿主、用户意图 → Repository 调用                   │
├───────────────────────────────────────────────────────────────────────────────┤
│ ⑤ 状态管理层（ArkUI 状态管理 V2）                                              │
│   @ObservedV2 / @Trace 领域对象 + @Local / @Param / @Provider / @Consumer      │
│   职责：字段级精准刷新；视图状态（看第几周、看哪个教师）与业务数据分离            │
├───────────────────────────────────────────────────────────────────────────────┤
│ ④ 仓储编排层（repository/）                                      ← 新增         │
│   ScheduleRepository · TodoRepository · SchedulePackage · SeedData · 两个 Importer │
│   职责：**事务边界**、对象图组装与差量同步、冲突策略、当前指向维护、工厂读数据    │
├───────────────────────────────────────────────────────────────────────────────┤
│ ③ 数据访问层（dao/）                                             ← 新增         │
│   SemesterDao · ScheduleTemplateDao · TeacherDao · CourseDao · ClassInfoDao    │
│   TimePeriodDao · StudentDao · AppSettingDao · LessonDao（读模型）              │
│   AttendanceDao（签到）· TodoDao（待办）                                      │
│   职责：单表（或强归属表组）的 SQL 与 Row 映射；不含业务判断                     │
├───────────────────────────────────────────────────────────────────────────────┤
│ ② 数据库基础设施层（db/）                                        ← 新增         │
│   ScheduleDb（连接/schema/迁移/事务/备份）· TableSchema（DDL 唯一真源）          │
│   DbExecutor + RsReader（执行器抽象与类型安全读取）· DbMigrations              │
│   职责：连接生命周期、建表、版本迁移、事务执行器、ResultSet 类型边界             │
├───────────────────────────────────────────────────────────────────────────────┤
│ ① 领域模型层（model/）+ 领域服务（service/）                                    │
│   Course / ClassGroup / TimePeriod / Teacher / Semester / SemesterCourses      │
│   ScheduleTemplate / Student / ClassInfo / ClassRoster / AppSetting            │
│   Attendance / TodoTask / TodoSubtask                                          │
│   ConflictDetector（时间冲突检测）· LessonReminder（提醒调度）· DateUtil · Util │
│   职责：纯业务语义与算法，不依赖任何存储细节                                     │
└───────────────────────────────────────────────────────────────────────────────┘
```

### 2.2 依赖约束（架构铁律）

```
⑦ 宿主 ──▶ ⑥ 页面 ──▶ ⑤ 状态 ──▶ ④ Repository ──▶ ③ DAO ──▶ ② DB 基础设施 ──▶ ① 领域模型
                                                                                  ▲
                                    ① 领域模型被所有层引用（只读类型）────────────┘
```

| # | 铁律 | 违反后果 |
| :--- | :--- | :--- |
| R1 | 页面层**不得**直接调用 DAO，更不得出现 SQL | 事务边界被打散，业务规则散落 |
| R2 | DAO **不得**依赖领域对象构造，只返回 `*Row` | 表结构变更波及领域层 |
| R3 | 领域模型**不得** import `@kit.ArkData` / `fileIo` | 领域层被存储污染，无法单测 |
| R4 | 只有 `ScheduleDb` 能拿到 `RdbStore` 实例 | 连接泄漏、多份 schema 认知 |
| R5 | 事务边界只能由 Repository 决定 | 出现"改了一半"的数据 |
| R6 | 任何模型都不得持有"文件路径" | 回到文件名当关联键的老路 |

**当前合规性**：R1 ~ R6 全部满足。`pages/` 只调用 `ScheduleRepository` / `TodoRepository`；
`model/` 与 `service/` 中不存在任何 `@kit.ArkData` 或文件 API 引用。

### 2.3 横切关注点

| 关注点 | 落地方式 |
| :--- | :--- |
| **日志** | `common/Logger.ets` 统一出口，domain `0x0A01`，tag 前缀 `WSD_`（WisdomDaily），可用 `hdc shell hilog -T WSD` 过滤 |
| **错误处理** | 统一 `errText()` 把异常转成 `code=…, message=…`；数据库异常向上抛，由页面转成用户可读提示 |
| **事务** | `ScheduleDb.runInTransaction<T>()`，回调抛异常自动回滚 |
| **类型边界** | `RsReader` 把 `ResultSet` 的列映射成确定类型，空值走兜底，替代旧版 `JSON.parse` 后的类型补齐 |
| **主键生成** | `newUuid()`（`util.generateRandomUUID`），业务主键与自增主键分离 |
| **颜色归一化** | `normalizeColor()` + 数据库 CHECK 约束双层拦截 8 位色值 |
| **命名与顺序** | 业务顺序一律落 `sort_order` 列，不依赖插入顺序 |
| **国际化/主题** | `resources/base` + `resources/dark`；`app_setting.theme_mode` 持久化用户选择 |
| **多端适配** | `deviceTypes: phone / tablet / 2in1`；课表网格按可用宽度与节数算列宽 |

## 3. 核心模块设计

### 3.1 模块清单与职责边界

| 模块 | 目录 | 文件数 | 职责 | 明确不做什么 |
| :--- | :--- | ---: | :--- | :--- |
| 数据库基础设施 | `db/` | 5 | 连接、DDL、索引、视图、迁移、事务执行器、备份 | 不知道任何业务规则 |
| 数据访问 | `dao/` | 11（+ `DaoSupport`） | 单表 SQL、Row 映射、批量写、级联删除 SQL | 不开事务，不组装对象图 |
| 领域模型 | `model/` | 9 | 实体与聚合、clone、行对象接口、业务方法 | 不认识数据库 |
| 领域服务 | `service/` | 2 | 冲突检测（教师维度 + 班级维度）；上课提醒调度（读课表 → 登记系统代理提醒） | 不写库 |
| 仓储编排 | `repository/` | 6 | 事务边界、对象图组装、种子数据、旧数据迁移 | 不写 SQL 字符串以外的表细节 |
| 公共 | `common/` | 7 | 日志、日期、工具（UUID/颜色/名称/周次） | 不含业务规则 |
| 宿主 | `entryability/`、`entrybackupability/`、`entryformability/` | 3 | 开库初始化、窗口装载、备份扩展 | 不碰业务 |
| 卡片层 | `widget/`、`entryformability/` | 4 + 1 卡页 | 卡片数据装配（只读库）、尺寸与版式、点击跳转 | 卡片进程**绝不写库** |
| 页面层 | `pages/` | 6（5 个注册路由页 + `Todo` 面板组件） | 布局与交互、`router` 跳转、半模态 | 不碰 SQL；不持有 `DbExecutor` |

### 3.2 核心模块职责表

| 模块 | 关键类 | 对外契约 | 关键设计点 |
| :--- | :--- | :--- | :--- |
| DB 基础设施 | `ScheduleDb` | `init(ctx)` / `runInTransaction<T>(work)` / `backup(name)` / `close()` | 单例 + `opening` 合流，并发 `init` 只开一次连接 |
| | `TableSchema` | `DDL_TABLES` / `DDL_VIEWS` / `DDL_INDEXES` / `DB_VERSION` | 表结构唯一真源；建表顺序即外键依赖顺序 |
| | `DbExecutor` / `RsReader` | 统一执行接口 + 类型安全读取 | 让同一段 SQL 既能走连接也能走事务 |
| 数据访问 | 10 个业务 DAO + 1 个读模型 DAO | 静态方法，首个参数一律 `DbExecutor` | 全部 `try/finally` 关闭 `ResultSet` |
| 领域模型 | `SemesterCourses` | 聚合根，持有 `teacher_courses[]` | 与旧版同构，但由多条 SQL 组装而来 |
| | `TimePeriod` | `overlaps()` / `coversWeek()` / `conflictText()` | 冲突判定含周次交集，修掉旧版漏判 |
| 领域服务 | `ConflictDetector` | `check(exec, …, candidate, exclude)` | 周次交集**下推到 SQL**，索引命中 |
| | `LessonReminder` | `sync(ctx, force?)` / `ensureNotificationEnabled(ctx)` | 提醒状态**不入库**：每次按课表重算一份快照，`cancelAllReminders()` 全清后重发（见 `docs/06` §2.8）；只在应用进程调用，自带节流与 try/catch |
| 仓储 | `ScheduleRepository` | 见 §3.3 | 唯一的事务边界决定者 |
| | `SeedData` | `seedIfEmpty(exec)` | 出厂数据直接 INSERT，不再走 rawfile |
| | `LegacyJsonImporter` | `hasLegacyData()` / `run()` / `archiveLegacyData()` | 一次性单向搬迁，幂等可重入 |

### 3.3 仓储对外接口（页面层的唯一依赖面）

```ts

├── 生命周期   init(ctx) · isReady() · close() · importLegacyData(ctx)
├── 读         loadWorkspace() · loadSemesterCourses(id) · loadRoster(classId)
│              loadWeekLessons(semesterId, teacherId, week) · stats(id) · populationReport(id)
├── 当前指向   savePointers(semesterId, teacherId) · setThemeMode(mode)
│              saveUiColors(theme, today) · saveReminderSettings(nextDay, ahead, minutes)
├── 学期       createSemester(...) · updateSemester(s) · deleteSemester(id)
├── 教师       upsertTeacher(semesterId, t) · deleteTeacher(id)
├── 课程       insertCourse(...) · updateCourse(c) · deleteCourse(rowId)
├── 班级分组   upsertClassGroup(courseRowId, g) · deleteClassGroup(groupId)
```

**页面层因此完全看不到 SQL、事务、表名。** 新增页面只需调用 Repository，
不必理解 14 张表的关系。

## 4. 核心数据流

### 4.1 读路径：冷启动装配

```
EntryAbility.onCreate
  └─ ScheduleRepository.init(ctx)                       ← 幂等，页面侧 await 同一个 Promise
       ├─ ScheduleDb.init(ctx)
       │    ├─ getRdbStore  { name:'wisdomdaily.db', securityLevel:S1 }
       │    ├─ PRAGMA foreign_keys / journal_mode / synchronous
       │    └─ version==0 ? 建表建视图建索引（一个事务）: 按需迁移
       └─ runInTransaction
            ├─ 有旧 JSON 且库为空 ? LegacyJsonImporter.run()  → 提交后归档旧文件
            └─ 否则 SeedData.seedIfEmpty() + AppSettingDao.ensureRow/repairPointers

页面 aboutToAppear
  └─ loadWorkspace()                                    ← 3 组轻查询
       semester 列表（JOIN 模板取名） · 模板+节次（一次查全部再分发，避免 N+1） · app_setting
         │
         ├─ 定位当前学期：app_setting.semester_id（主键）→ 找不到则 repairPointers 兜底
         ▼
  └─ loadSemesterCourses(semesterId)                    ← 6 条直查 + 内存拼装
       teacher → course → class_group → time_period → period_week
       逐层用 Map 归组：periodsByGroup → groupsByCourse → coursesByTeacher
         ▼
     SemesterCourses{ semester, teacher_courses[ { teacher, courses[ { class_groups[ { time_periods } ] } ] } ] }
         ▼
  └─ loadWeekLessons(semesterId, teacherId, week)        ← 切周时走 v_lesson 视图，只取本周
         ▼
     页面渲染：周一~周日 × 第 1~N 节 网格，按 time_period 定位课块
```

**读路径的两级策略**（这是关系库方案的关键设计）：

| 场景 | 走法 | 为什么 |
| :--- | :--- | :--- |
| 冷启动装配整学期对象图 | 6 条直查 + 内存拼装 | 视图按周展开会膨胀数十倍行数 |
| 切周 / 切教师后的刷新 | `v_lesson` 视图按 `(semester, teacher, week)` 取 | 一条索引查询拿到本周全部课，含班级名与颜色 |
| 左右滑动"跟手预览"相邻周 | 切周时**顺带**预载相邻两周（`prevLessons` / `nextLessons`） | 手指推出去要立刻看到真实课表，不能等松手才查；翻页后三份数组就地轮转，零查询 |

### 4.2 写路径：编辑即时落库

**这是相较旧版最本质的变化**。旧版是"改内存 → 用户点保存 / 三个生命周期回调里整学期覆盖写"；
现在**每一个编辑动作都是一次独立事务**，没有"待保存"状态。

```
用户改一个教室 / 一个周次
  └─ ScheduleRepository.deletePeriod / savePeriod(…)
       ├─ 【事务 A】冲突检测（读）
       │    ├─ 教师维度：SQL 收口 teacher_id + weekday + 节次相交 + pw.week_no IN (本次周次)
       │    └─ 班级维度：SQL 上再加 cg.class_id IN (本次班级)
       │    └─ 返回 ConflictHit[] 给界面
       ├─ 有冲突且 force=false  → 不写库，界面弹确认（**绝不静默丢弃**）
       └─ 【事务 B】写入
            ├─ period.id > 0 : UPDATE time_period + DELETE/INSERT period_week
            └─ period.id = 0 : INSERT time_period → last_insert_rowid() → INSERT period_week
```

| 编辑动作 | 事务内语句数 | 影响的表 |
| :--- | :--- | :--- |
| 改课程名 / 学分 | 1 | `course` |
| 改某时间段的教室 | 1 | `time_period` |
| 改某时间段的周次 | 1 + N | `period_week` |
| 新增时间段 | 2 | `time_period` + `period_week` |
| 新增课程 + 班级 | 3 ~ 4 | `class_info` + `course` + `class_group` |
| 删除课程 | 4 ~ 5 | 四张表自底向上 |
| 切换当前教师 | 1 | `app_setting` |

**结果**：一次编辑最多写几条语句，且原子生效。旧版则是"整学期序列化 + TRUNC 覆盖"，
改一个字符都要重写整棵对象图，且中途被杀就归零。

### 4.3 兜底同步：`syncSemesterCourses`（不再是唯一保障）

```
内存对象图（期望态）   ←→   数据库（当前态）
  ① 教学期/教师/课程：库里有 + 内存有 → UPDATE；库里没有 → INSERT
  ② 班级分组：按 (course_id, class_id) upsert
  ③ 时间段：按 id 判断 UPDATE / INSERT，周次整体替换
  ④ 清理：库里存在但内存已无的 时间段 → 班级分组 → 课程，自底向上删
  ⑤ 全程一个事务；产出 SyncReport{ +inserted / ~updated / -deleted / weeks / ms }
```

它现在的定位是**兜底与批量导入**（导入备份、外部数据批量导入、恢复后重建），
而不是日常保存路径。旧版把"整学期覆盖写"当成唯一写入方式，是所有数据事故的源头。

### 4.4 生命周期：不再需要"抢救式保存"

| 生命周期 | 旧版（JSON 存储） | 新版（关系库） |
| :--- | :--- | :--- |
| `onCreate` | 拷贝 rawfile 种子 → 读 `default_setting.json` → 读学期 JSON → 读模板 JSON | 打开库 + 首启初始化（一次性） |
| `onBackground` | **保存当前学期 + default_setting** | 空实现（数据已实时提交），仅打日志 |
| `onWindowStageDestroy` | **再次保存** | 空实现 |
| `onDestroy` | **第三次保存** | 释放数据库连接 |
| 全量重写次数 | 每次切后台最多 1 次整学期重写 | **0** |

> 三个回调都挂保存，本质是"因为不能保证下一次还能跑，所以每次都赌一把"。
> 事务化之后这个赌博没有必要了——真要丢数据，也只可能丢"用户正在编辑但还没点确定"的那一步。

### 4.6 提醒路径：课表 → 系统代理提醒（`LessonReminder`）

```
页面层 Index.refresh()（每次读库装配完课表）
   └─► LessonReminder.sync(context)                     ← 应用进程；20 秒节流
        ├─ 读 app_setting 三个提醒开关（都关 → 只做清理）
        ├─ 读当前学期 / 教师 / 作息模板
        ├─ 算「今天起 4 天」每天的课（按周缓存，避免重复查询）
        ├─ getValidReminders() → cancelAllReminders() → getValidReminders()
        │     ← 清点额度：系统把「已弹出但没点关闭」的也算有效，只有这里看得出额度被谁占着
        ├─ 收集两类待登记提醒 → 按触发时刻升序排队（额度紧时先保「马上要响」的）
        ├─ 登记「次日有课 → 当天 22:00」提醒
        └─ 登记「课前 N 分钟」提醒（今天 + 明天；课间 ≤ N 分钟的跳过）
             撞 1700002 → 立即停手并熔断 10 分钟（额度满了再发也只是刷日志）

「我的 → 上课提醒」拨开关 / 改提前量
   └─► ScheduleRepository.saveReminderSettings(...)      ← app_setting（schema v5）
   └─► LessonReminder.sync(context, force = true)        ← 绕过节流，立即生效

到点
   └─► 系统闹钟 → 通知（应用进程可以完全不在运行）
```

**两条约束写在数据流里**：

1. 提醒是**单向**的 —— 只有"课表变了 → 重建提醒"，提醒从不反过来影响课表。
   所以 `sync()` 内部整体包 try/catch，失败只落日志，不会把课表加载拖下水；
2. 提醒**不进数据库**。"发过哪些提醒"这种状态一旦持久化，就得处理"课表改了但提醒没跟上"的一致性问题；
   现在的做法是每次重建一份快照，库里永远只有课表这一个真源。
3. 提醒**额度不归应用管**：系统只放行 30 条"有效/未过期"的提醒，而"有效"包含
   **到点弹出后用户没点关闭**的那些。所以每条提醒都必须带一个关闭按钮（`actionButton`），
   并且每次重建都要清点额度 —— 否则额度只进不出，最后每条登记都撞 `1700002`
   （2026-09-22 真机日志，见 `docs/06` §2.8.5）。

### 4.7 待办路径：独立于课表的一条支流

```
页签切到「待办」/ 从 TodoEdit 返回
   └─► Index.onPageShow 自增 todoRefreshTick
        └─► TodoPanel @Monitor('refreshTick') → TodoRepository.loadTasks()
             ├─ purgeExpiredTrash()            ← 进页先清 30 天前的软删行（失败只记日志）
             ├─ 分组：逾期 / 今日 / 即将 / 无截止 / 已完成（组头计数）
             └─ 清单芯片 = 预设清单 ∪ 库内实际出现的 list_name

新建 / 详情保存（pages/TodoEdit，router 带 taskId）
   └─► TodoRepository.create(task) / saveEdit(task)
        └─ create/saveEdit 内单事务：todo_task 整行写 → todo_subtask 先删后插

勾选完成
   └─► TodoRepository.toggleDone(task)
        ├─ 非重复任务：只翻 done / done_at
        └─ 重复任务：同一事务里 ① 原条置完成 ② 克隆下一条（due_at 顺推、提醒重算、子任务照搬未完成）
             ← 克隆前查重：同标题 + 同规则 + 同截止且未完成已存在 → 跳过
                （撤销不回收克隆，没这道闸会越堆越多）

「学习」清单顶部当天课程
   └─► ScheduleRepository.loadTodayLessons()（只读，当前指针学期+教师、今天周次与星期）
        └─ 左滑完成 → LessonDoneStore（preferences 按天记账，不写库）
```

**为什么待办不复用 `ScheduleRepository`**：待办与课表**没有外键关系**，也不需要装配对象图，
塞进同一个门面只会让那个 1 577 行的类更臃肿；反过来，"学习清单要看当天课表"这一点由
`ScheduleRepository` 提供三个只读方法满足，两条支流不共享写路径。

## 5. 架构关键点

### 关键点一：事务边界收口在 Repository

DAO 只接受 `DbExecutor`，既可以传连接（自动提交）也可以传事务。
"该不该开事务"这个判断只有一处——Repository。这让 R5 成为可执行约束而非口号：
想绕过事务做多表写，必须显式构造 `StoreExecutor`，一眼就能在 Code Review 里看出来。

### 关键点二：`DbExecutor` 抽象让 SQL 与事务解耦

`RdbStore` 与 `Transaction` 是两套不兼容的类型。若 DAO 直接依赖 `RdbStore`，
"同一段 SQL 走事务"就得复制一遍代码。`DbExecutor` 接口把两者的同形方法收口，
于是 **DAO 只写一次，事务与连接两个场景都覆盖**。

### 关键点三：类型边界从"JSON.parse 之后补字段"移到"ResultSet 列映射"

```
旧：文件文本 ─JSON.parse→ 无类型对象 ─构造函数逐字段 ?? 默认值→ 领域对象     （类型风险在构造函数里）
新：ResultSet ─RsReader→ *Row（确定类型，空值显式）─fromRow→ 领域对象        （类型风险在 RsReader 里，只有一处）
```

好处是类型修复集中在一处：`RsReader` 的 `str/num/real/optXxx/bool` 六个方法
覆盖了全部类型转换，领域层的 `fromRow` 再也不用写 `?? 默认值` 防御。

## 9. 架构总结

### 9.1 一句话概括

**七层单向依赖 + 事务化行级写入 + 视图驱动的按周读取 + 双保险级联删除 +
一次性旧数据搬迁**。复杂度不在分布式，而在"编辑体验顺滑"与"进程随时可能被杀"之间的平衡——
而这个平衡点这次是**用关系库的事务**来锚定的。

### 9.2 做对的三件事

1. **把事务边界收口到 Repository**。DAO 不知道事务，页面不知道 SQL，
   "该不该开事务"只有一个决定点，规则可执行、可审查。
2. **`DbExecutor` 抽象**。让同一段 DAO 代码同时服务于"连接"和"事务"，
   避免了 DAO 复制两份，也让"绕过事务写多表"变成显式行为。
3. **用不可变主键取代名称关联**。`class_info.class_id`、`course.course_id`、
   `semester.id` 一旦生成就不再变，改名、重排、跨学期引用都不会断链。

### 9.3 必须继续做的三件事

| 优先级 | 事项 | 理由 |
| :--- | :--- | :--- |
| P0 | 按 [04-详细设计](04-详细设计.md) 实现页面层 | 数据层已就绪，页面是当前唯一阻塞项 |
| P1 | 冲突提示接入 UI 交互 | 数据层已返回 `ConflictHit[]`，需要界面把"确认覆盖"这条路径做出来 |
| P2 | 渲染缓存 + `period_week` 位图 | 容量翻倍时先做这两项，其余优化收益远低于此 |

### 9.4 演进方向

从"能存住数据"走向"数据能流动"：
导出（CSV / ICS 日历）→ 导入（教务系统课表）→ 多设备（系统备份 → 分布式数据同步）。
关系库是这条路径的前提——旧 JSON 方案连"按条件查出一部分数据"都做不到。
